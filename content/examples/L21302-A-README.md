# L21302-A：零售推薦與製造檢驗的介接請求

`L21302-A-requests.json` 是本組六頁共用的教學合成資料，沒有真實個資、影像或存取憑證。固定值用來核對資料流、錯誤分支與業務狀態，不能當成模型品質或產品效能量測。

## 固定規則

- 零售 r01～r12、製造 m01～m12，各 12 筆，依尾碼 1～12 固定回放。
- `seed=21302` 是全組保留的共用種子；本版採明列值，沒有亂數抽樣。
- `split.contract_smoke=[1,2,3,4,5,6,7,8]`、`split.regression=[9,10,11,12]` 是介面回放分組，兩領域共用；不是模型訓練／驗證／測試切分。
- API 契約 v1、特徵規則 f1，模型分別是 rec-v2 與 inspect-v3；資料版本分別是 retail-d1 與 manufacturing-d1。
- 憑證→動作權限→媒體格式→必填欄位依序檢查。所有請求一次只安排一種預期 API 錯誤，避免分支順序造成不同答案。
- `credential` 只是可信上游驗證結果的測試替身，不是真實 token，也不能當成用戶端可自行宣告的權限。
- 模型替身把 `body.feature` 當成固定輸出分數，並非機器學習算法。程式只驗證介接行為。
- `expected_status` 與 `expected_response` 是預先設計、再由獨立回放核算的契約答案，不代表 HTTP 請求實際送出。
- 分數至少 0.80 才符合業務動作門檻；第 10 筆下游逾時，動作尚待確認，其餘合格請求完成動作。
- `feature_ttl_s=5` 是教學的新鮮度門檻。此契約仍允許過期特徵的預測回傳，時效警報另行處理，並非推薦的通用上線政策。

## 欄位意義

| 欄位 | 意義 | 單位或限制 |
|---|---|---|
| request_id／entity_id | 請求與會員／工件識別 | 合成 ID，請求 ID 全檔唯一 |
| source | 管線來源類型 | warehouse、lake、iot、third_party_api |
| method／path／content_type | HTTP 介面契約 | 本資料用 POST＋JSON；第 8 筆格式故意錯誤 |
| api_version／model_version | 介面與實際模型版本 | 兩者分開管理 |
| dataset_version／feature_version | 資料與特徵規則版本 | 可追溯的教學標記 |

| 欄位 | 意義 | 單位或限制 |
|---|---|---|
| event_time_s | 來源事件發生時間 | 合成相對秒數 |
| feature_time_s／request_time_s | 特徵更新／呼叫時間 | 差值用來檢查新鮮度 |
| credential／scopes | 可信憑證狀態與動作權限 | 僅為模擬驗證結果 |
| body | 提供實體 ID 與合成特徵 | 第 5 筆缺 feature |
| predicted_score | 模型替身回傳分數 | API 拒絕時為 null |

| 欄位 | 意義 | 單位或限制 |
|---|---|---|
| expected_status／expected_response | 預期 HTTP 狀態與回應本文 | 200、401、403、415、422 |
| expected_error | 更細的失敗原因 | 缺憑證、過期、權限、欄位或媒體格式 |
| department | 接手業務部門與系統 | 行銷／CRM、品管／MES |
| business_action／business_error | 動作狀態與下游錯誤 | 逾時不可假設尚未執行或已完成 |
| lifecycle／procurement | 更新場景與獨立需求預測 | 採購不是由推薦或瑕疵分數換算 |

`source` 僅標示上游來源種類，不宣稱資料已由程式實際連線擷取。零售來源也可包含店內感測，製造來源也可包含整理後倉儲，兩者故意使用同一輪來源索引方便比較。

## 關鍵參考數值

| 每一領域 | 筆數 | 索引 |
|---|---|---|
| API 200 | 7 | 1、2、7、9、10、11、12 |
| API 401 | 2 | 3 缺少憑證、6 已過期 |
| API 403 | 1 | 4 缺 predict |
| API 415 | 1 | 8 格式不接受 |
| API 422 | 1 | 5 缺 feature |

兩領域共 24 筆：200 共 14、401 共 4、403／415／422 各 2。每一領域符合分數門檻 3 筆（1、10、12），已完成動作 2 筆（1、12），待確認 1 筆（10）。

r01／m01：第 103 秒請求、第 101 秒更新特徵，落後 2 秒。r07／m07：第 109 秒請求、第 90 秒更新，落後 19 秒。每領域各有 1 筆過期特徵，該筆仍是 API 200。

獨立的採購案例：demand-v1 預測 120 件、現貨 80 件、安全庫存與在途量均不納入，草案 40 件，必須人工核可。製造案例的「完成動作」只表示送複檢，不是真實瑕疵標籤。
