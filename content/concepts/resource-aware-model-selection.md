## 為什麼需要

驗證誤差最小的模型，可能放不進邊緣裝置，也可能來不及回應。若等到訓練完才檢查硬體，選模結果就可能無法上線。

資源與延遲限制下的模型選擇（Resource-aware Model Selection）把部署預算提早放進比較。先找到能執行的候選，再在其中平衡預測效果、速度與維運成本。

## 直覺

像先檢查設備能不能裝下、能不能準時完成工作，再比較完成品質。記憶體與延遲是不同限制，滿足其中一項不代表另一項也合格。

:::supplement[來源：本站 L23302-A 教學合成資料]
圖中延遲、峰值記憶體與分數均為模擬假設，不是模型或硬體 benchmark。數字只用來練習篩選，不能推論 TCN 在所有裝置上都比 GRU 快。
:::

## 定義與公式

指引把部署分成資源受限、資源充足及即時推論三種考量，即時任務要求秒級或毫秒級回應。小型模型、壓縮、快取與蒸餾都只是候選方法，仍需檢查效果與實際成本。

### 比較前先定義量測（補充）

| 指標 | 代表什麼 | 不能直接代替什麼 |
|---|---|---|
| 模型檔大小 | 儲存與下載的大小 | 執行時峰值記憶體 |
| 峰值記憶體 | 執行期間最高佔用 | 只有權重的儲存量 |
| 核心推論時間 | 模型運算本身 | 使用者端到端等待 |
| 端到端 p95 | 95% 請求在此時間內完成 | 平均值、最慢值或絕對時限 |

端到端包含取得輸入後的前處理、傳輸、排隊、模型與後處理。若業務有每次都不能逾時的硬限制，p95 仍不足以保證，要另定最壞情況與超時處置。

## 走一次流程

### 同任務的三種預算（補充）

共用 `L23302-A-weekly.json` 以同樣三摺能源目標比較候選，MAE 越低越好。三種部署輪廓的硬體各自不同，下面都是固定假設，不是把同一次計時套到三種硬體。

| 部署輪廓 | 假設硬體 | 端到端 p95 上限 | 峰值記憶體上限 |
|---|---|---|---|
| 邊緣裝置 | 裝置 CPU、單筆推論 | 15 ms | 64 MiB |
| 雲端服務 | 伺服器 CPU、單筆含傳輸 | 30 ms | 256 MiB |
| 即時本地 CPU | 本地 CPU、單筆低延遲 | 10 ms | 128 MiB |

候選的模擬資源卡如下。雲端欄已把傳輸與服務流程納入假設；峰值記憶體則刻意假設各輪廓相同，實測時必須分別量。

| 候選 | 能源 MAE／檔案 MiB | 邊緣／雲端／即時 p95（ms） | 峰值 MiB |
|---|---|---|---|
| 落後值線性模型 | 8／4 | 4／9／4 | 20 |
| 小型 GRU | 7／12 | 18／13／18 | 80 |
| 小型 TCN | 6／8 | 12／11／12 | 48 |

1. 邊緣先排除 GRU，因為 18 ms 與 80 MiB 都超標。線性與 TCN 留下，TCN 的 MAE 較低。
2. 雲端三個都符合預算，若以最低 MAE 選擇，也是 TCN；資源充足不代表必須選最大模型。
3. 即時輪廓只有線性模型符合 10 ms。不能因 TCN 誤差較低就直接忽略時限。
4. 製造資料使用同一切分，模擬 MAE 平均分別為 0.08、0.07、0.06 mm/s；單位不同，不能拿來與 kWh 誤差直接排名。

## 程式（補充）

程式只讀取固定模擬卡做條件核算，沒有呼叫計時器。若全部候選不符合預算，應回報沒有可行候選。

```python
import json, os
from pathlib import Path
root = Path(os.environ.get("IPAS_REPO_ROOT", "."))
d = json.loads((root / "content/examples/L23302-A-weekly.json").read_text(encoding="utf-8"))
def score(card):
    return sum(card["energy_fold_mae"]) / len(card["energy_fold_mae"])
for p in d["profiles"]:
    ok = [c for c in d["cards"] if c["peak_mib"] <= p["budget_mib"] and c["p95_ms"][p["id"]] <= p["budget_ms"]]
    winner = min(ok, key=score)["id"] if ok else "無可行候選"
    print(p["name"], "→", winner)
```
```text
邊緣裝置 → tcn-small
雲端服務 → tcn-small
即時本地 CPU → linear-lag
```

:::tip[讀碼重點]
先用 `ok` 檢查兩項硬限制，再以驗證分數選擇。若要改權衡方式，先明確區分必須通過的限制與可以折衷的偏好。
:::

## 怎麼用、怎麼判讀

### 優化入口

| 情況 | 可先比較的方法 | 要再確認的代價 |
|---|---|---|
| IoT、手機、邊緣資源不足 | 簡單模型、小型網路、剪枝、量化 | 效果與硬體是否受益 |
| 雲端與資料中心 | 深度模型、集成、較完整前後處理 | 費用與維運負擔 |
| 金融交易、推薦要即時 | 快取、模型蒸餾 | 新鮮度、效果與回應時間 |

:::supplement[來源：ONNX Runtime Tune performance；PyTorch Benchmark 教學]
剪枝後是否變快，取決於執行環境能否利用稀疏或縮小的結構；量化也需支援低精度的算子。快取只適用於可重用且仍有效的輸入，模型或資料更新後要考慮失效規則。
:::

### 延遲實測設計（補充）

固定硬體、執行環境、輸入形狀、批次大小與併發量，使用同一批請求。模型切到推論狀態，先暖機再重複量；冷啟動另外保留，不能直接刪掉不報。

分開記核心與端到端時間，若用 GPU，還要處理非同步執行造成的計時差異。報告 p50、p95、超時比例與峰值記憶體；必要時也看吞吐量及尖峰負載，重新驗證壓縮後效果。

### 換個場景

| 場景 | 判讀重點 |
|---|---|
| IoT、手機 App、邊緣裝置 | 儲存、記憶體與推論速度都有限 |
| 雲端、資料中心 | 可用較複雜模型，但仍有成本 |
| 金融交易、推薦 | 即時回應需求優先，快取與蒸餾可比較 |
| 能源閘道器（補充） | 能否在本地預算內完成下一週需求估計 |
| 製造控制訊號（補充） | 尾端延遲之外，還需定義超時行為 |
| 農業離線裝置（補充） | 網路不可用時仍須完成必要推論 |

## 常見誤解

- 「雲端算力多就沒有延遲限制。」傳輸、排隊與成本仍在。（補充）
- 「模型檔小就一定快。」算子、記憶體存取與硬體支援都會影響。（補充）
- 「量化或剪枝後必定加速且效果不變。」要重新量測與驗證。（補充）
- 「p95 達標就是每次都不逾時。」它仍容許尾端請求更慢。（補充）

## 小結

- 把部署預算放進選模，先篩可行候選。
- 分清檔案大小、峰值記憶體、核心與端到端延遲。
- 同硬體與負載下量測，分位數不能取代絕對時限。
- 壓縮、快取與蒸餾都要重新確認效果及成本。
