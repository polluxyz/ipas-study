## 為什麼需要

零售推薦模型上線時很好用，幾週後卻可能跟不上新商品。製造檢驗模型也可能在更換相機後失準。程式沒有修改，不代表模型面對的資料沒有改變。

指引把資料變化造成模型不再適用的現象稱為模型漂移（Model Drift）。部署時也要顧及延遲、可用性、可說明性與合規要求。

MLOps（Machine Learning Operations）把模型開發與日常維運串成持續循環。目標是讓模型能被測試、交付、監控與更新，並保留足夠紀錄追查每次變動。

## 直覺

先把模型當成「需要持續維護的服務」。訓練只產生候選模型；接著要檢查能否上線，上線後還要確認服務與預測是否持續符合需求。

![注意監控之後還有資料檢查與回訓，候選模型每次都必須通過驗證。](figure:l21302-mlops-lifecycle-loop)

生命週期包含回訓與優化，不是每次都從頭重跑。監控發現的可能是資料缺欄、服務壅塞或模型品質下降，處置方向要先看原因。

## 定義與公式

MLOps 是把 DevOps 的開發與營運協作延伸到機器學習。除了程式，還要管理資料、訓練產物、測試與線上服務之間的關係。

| 要求 | 在生命週期中的做法 | 能回答什麼 |
|---|---|---|
| 自動化 | 由觸發條件串起訓練、測試與部署 | 哪些步驟可以一致執行？ |
| 可重現 | 保存資料、設定與模型成果 | 如何重做當時的實驗？ |
| 可追溯 | 將模型版本連回測試及部署紀錄 | 目前結果來自哪次交付？ |

:::supplement[來源：Google Cloud MLOps 的 Data and model validation、Metadata management；PyTorch「Reproducibility」]
可重現還需要程式、執行環境與隨機種子等條件。保存了資料與設定，重跑結果仍可能因運算順序、硬體或函式庫版本而有細微差異，不保證逐位元相同。

資料格式驗證、模型品質驗證與 API 相容性檢查應有各自門檻。更新失敗時，保留現行版本及回退線索，比只留下最新權重更有用。
:::

## 走一次流程

### 用零售與製造走完循環

先準備資料、訓練與測試，再驗證及部署；營運後持續監控，將回饋帶回回訓與優化。通過測試門檻，才交付候選模型。

:::supplement[來源：Google Cloud MLOps 的 Data and model validation、Metadata management；教學合成資料 L21302-A]
共用資料是教學合成請求，零售模型為 rec-v2、製造為 inspect-v3，各有 12 筆。它們用來檢查介接行為，不能估計真實品質。

資料檔：`content/examples/L21302-A-requests.json`。

1. **資料準備**：固定 retail-d1／manufacturing-d1 與特徵規則 f1，保留來源及時間。
2. **訓練與測試**：新商品或相機變動後，建立 rec-v3／inspect-v4 候選版本；不能只改檔名就稱為重訓。
3. **驗證**：品質用另行準備的標註資料評估；本組請求則檢查契約及錯誤處理，兩者都要過門檻。
4. **部署**：把通過驗證的候選版交給推論服務，記錄實際載入的模型版本。
5. **監控回饋**：看輸入、服務錯誤與有標籤的預測品質，再決定修資料、修系統或回訓。

例如 r03 缺少憑證而遭拒，先修存取設定；r07 特徵過舊，先查資料更新。這兩種錯誤都不能單靠重新訓練模型解決。
:::

## 怎麼用、怎麼判讀

當模型更新頻繁、需要長期追蹤資料變化，或多個團隊共同交付時，就需要明確的 MLOps 流程。重點是讓每階段的輸入、驗收與責任可以接起來。

### 換個場景

| 場景 | 要觀察的變動 | 生命週期上的處置 |
|---|---|---|
| 指引：資料持續變化的營運服務 | 原有模型可能不再適用 | 監控、回饋、版本管理與更新 |
| 零售推薦（補充） | 新商品與促銷改變需求 | 回收互動資料，再驗證候選版 |
| 製造檢驗（補充） | 相機與光源改變輸入 | 先查資料品質，再蒐集標註 |
| 客服分類（補充） | 新產品帶來新問題類型 | 修訂標籤與測試後再發布 |

### 先查哪一層（補充）

API 回傳成功只代表服務完成約定的處理，不能證明推薦有用。沒有真實結果標籤時，可以先看資料與服務訊號，但要等回饋到齊才能判定品質是否下降。

## 常見誤解

- **「上線就結案。」** 資料與環境還會變，模型需要持續維護。
- **「自動化就是直接上線。」** 自動流程仍要有測試與驗證門檻。
- **「看到警報就重訓。」** 應先分辨資料、服務與模型問題，避免把系統錯誤當成模型失準。（補充）
- **「保存權重就能重現。」** 還需要資料、程式與環境等來源條件。（補充）

## 進階

### 與其他頁面的分工

持續整合、持續部署負責變更交付；實驗追蹤負責保留訓練設定與成果。它們是生命週期中的工作，本頁先掌握各階段為何必須連起來。

## 小結

- 模型上線後仍會受到資料與環境變化影響。
- 訓練、測試、部署與監控要串成可持續運作的循環。
- 自動化、可重現與可追溯回答不同問題，三者需要一起安排。
- 監控異常先查原因，通過驗證的候選版才發布。（補充）
