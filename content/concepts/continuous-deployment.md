## 為什麼需要

人工逐台複製權重可能漏換版本，也可能放錯檔案。持續部署的英文為 Continuous Deployment，簡稱 CD，將通過測試的產物送往目標環境。

指引強調：候選模型先通過測試，再自動送往測試或生產環境。A/B 測試與藍綠部署則用來協助控制發布風險。

## 直覺

先確認「哪一份產物通過驗證」，再確認「要送去哪裡」。自動部署也要有門檻，不能把訓練完成當成上線資格。

![測試門檻在交付之前，藍綠與 A/B 位於受控上線階段，監控仍可把流程帶回舊版。](figure:l21302-continuous-deployment-promotion)

回復（指引稱回退，Rollback）讓異常服務切回先前版本或預設邏輯，對應指引 3-58 的容錯安排。

:::supplement[來源：Google Cloud MLOps「Continuous delivery」；Google SRE「Canarying Releases」]
圖中的固定產物與人工核可選項，是把指引原則展開成可執行的發布流程。環境切換與成效分流可以組合，但不是每次發布都必須同時使用。

## 定義與公式

CD 接手通過測試門檻的模型，部署到約定環境。AI 持續整合與品質門檻回答「產物是否合格」，交付流程則管理「合格產物何時、如何進入環境」。

### 持續交付和持續部署（補充）

持續交付（Continuous Delivery）維持可發布的產物，正式上線可以保留人工核可。持續部署會在所有自動門檻通過後自動進入生產環境。兩者都不是取消驗證。

本頁的持續部署對應指引 CD；持續交付則是另一種保留核可的安排。看到流程中的人工核可時，應依實際控制點判讀，不只看縮寫。

## 走一次流程

先通過單元、品質與效能測試，再將模型部署至測試或生產環境。藍綠可用於新舊環境切換，A/B 可在發布後比較不同輸出的效果。

### rec-v3 的一次交付（補充）

使用 `L21302-D-releases.json` 的零售版本。rec-v3 通過 20／20 測試，驗證準確率 95%，離線 p95 為 110 ms，符合這次發布標準。

1. 封存 `retail-release-2`，綁定模型、資料、程式雜湊值與測試報告。
2. 在測試環境載入同一份模型，檢查 API v1 與特徵規則 f1。
3. 需要人工核可的團隊，在此留下核可人與時間；自動部署則檢查全部政策條件。
4. 採藍綠時，先準備新環境並測試，再切換入口；舊環境暫留作回復點。
5. 若要比較推薦點擊成效，另設 A/B 分組、曝光與點擊紀錄。監控不達標時停止擴量或回復。

rec-v4 的單元測試未全過，所以連第一步交付資格都沒有。不能把它放進新環境後，再用少量使用者替代已失敗的測試。

## 怎麼用、怎麼判讀

指引場景是通過測試的模型要送往測試或生產環境。判讀流程時，先找測試門檻，再找目標環境與發布策略；缺少前者，就沒有「通過才部署」的保證。

### 換個場景

| 場景 | 交付安排 | 判讀重點 |
|---|---|---|
| 指引：測試或生產環境 | 合格模型自動交付 | 測試是必要前提 |
| 指引：需控制發布風險 | 配合 A/B 或藍綠 | 分流比較或環境切換 |
| 零售推薦（補充） | 發布後比較點擊 | 版本與曝光要可追蹤 |
| 製造檢驗（補充） | 先在指定產線驗收 | 現場延遲與復原程序 |
| 金融風控（補充） | 上線前保留核可關卡 | 核可綁定明確產物 |

### 發布前的回復準備（補充）

回復點要包含模型、服務程式、特徵規則與路由設定。若新程式已改成舊模型不認得的輸入，只換回權重仍會失敗；資料庫改動也須保留相容路徑。

## 常見誤解

- **「自動化就沒有門控。」** 自動流程仍以通過測試為前提。
- **「進入測試環境等於全面上線。」** 測試和生產是不同交付目標。
- **「藍綠切換就能證明點擊改善。」** 切換主要管理環境，因果比較還需合適實驗。（補充）
- **「重建同名檔案可以沿用報告。」** 內容變了，就須重新確認證據。（補充）

## 進階

### 門控失敗要留下什麼（補充）

記錄被阻擋的發布清單、失敗條件與目前正式版本。修正後重新驗證，不把舊報告改寫成通過；模型登錄與版本狀態可保存這些管理紀錄。

## 小結

- CD 必須接在測試門檻之後。
- 部署至測試環境與部署至生產環境要分開確認。
- A/B 與藍綠可配合流程控制風險。
- 保留人工核可與否，決定交付和自動部署的控制方式。（補充）
