## 為什麼需要

能合成一句話，不代表能交付一套語音教材或客服服務。還要選音色（聲音的可辨特徵）、確認語言、整理稿本，並檢查情緒及聲音使用的權利。

語音合成服務與應用規劃把用途轉成可驗收的條件。指引特別提醒情感自然度、多語言與方言品質，以及語音複製（亦稱聲音複製）的隱私與偽造風險。

## 直覺

先問「誰對誰說什麼」，再問「用哪個平台」。教材重視長段一致性，客服重視業務內容與即時回應，同一個宣傳分數無法回答全部問題。

角色是劇情中的人物，指定由誰發聲的模型輸入則稱為語者條件。多語者代表多個說話者，不能用它代稱多語言支援。

## 定義與公式

指引列出四種常見平台，以下保留它們的應用定位，不把品牌當成品質保證。

| 平台 | 指引定位 | 優先比較的需求 |
|---|---|---|
| ElevenLabs | 情感、多語言及風格調整 | 角色對白、Podcast |
| Microsoft Azure TTS | 企業級擴展、多語及語音風格 | 商業客服、導航 |
| Google Cloud TTS | 可擴展 API、多語言及語音客製化 | 智慧助理、客服機器人 |
| Amazon Polly | 多語言、多音色及規模化 | 有聲書、虛擬助理 |

:::supplement[來源：ElevenLabs、Microsoft Azure、Google Cloud、Amazon Polly 官方 TTS 文件]
可量測的比較條件包括：指定語言是否可用、角色音色是否一致、同一稿本的聽評、錯詞、首段與完整音訊延遲。再記錄介面、音檔格式、服務版本與測試日期。

平台功能會依模型、語言、區域與方案而異。查到支援「情緒」後，還要測指定語言與音色；不能推論所有組合都支援。
:::

### 語音複製與一般音色選擇

語音複製（Voice Cloning）試圖重現特定人的聲音特徵。和選用一般服務音色相比，它更容易造成身分誤認，必須確認聲音來源及獲准用途。

:::supplement[來源：Microsoft Azure TTS 官方文件；C2PA FAQ；GAO「Combating Deepfakes」]
規劃紀錄至少區分稿本來源、錄音來源、音色使用同意、發布用途及到期／撤回處理。服務允許建立音色，不代表任意取得的錄音都能使用。
:::

## 走一次流程

### 同一份資料走到交付

:::supplement[來源：共用教學資料 L21103-F-speech.json；四平台官方 TTS 文件]

本組有有聲教材 E01–E10、客服 C01–C10，各 10 段。語言、音色、情緒與來源紀錄共用同一份 JSON；沒有真人聲音與實測分數。

1. **定用途與來源。** E01 要課程旁白；C01 要訂單回應。各自查稿本、音色來源與允許發布的欄位。
2. **固定比較條件。** 用 01–06 調設定、07–08 驗證，選定方案後才用 09–10 檢查，避免只挑到適合看過稿本的方案；候選服務使用相同索引。
3. **準備語音條件。** 先固定 zh-TW、speaker-A、正常語速及中性情緒，再單獨改語速或風格，不一起更換全部條件。
4. **查風險案例。** 04 是方言，需方言使用者聽評；E05 檢查緊急語句，C05 檢查否定詞；08 的設定音色與預期不同，要退回修正。
5. **選方案再交付。** 比較品質、錯詞與延遲，並測連線失敗時的文字回應。10 的模擬同意未開放發布，即使品質合格也先停止交付。

種子 42 只在可設定的模型或服務上固定；不能設定時，記錄模型版本與測試日期，不宣稱輸出可完全重現。

E01 的假設首段延遲是 260 ms；C01 是 180 ms。這些只能示範量測端點與需求比較，不能證明某平台比較快。
:::

### 多語與情緒測試

指引要求面對不同語言、方言及情緒時仍保持品質。不要只測一種語言的中性短句。

:::supplement[來源：Hugging Face Audio Course「Evaluating text-to-speech models」；ElevenLabs TTS 官方文件]
固定同一段業務意思，分別測華語、英語與台語；各語種由熟悉該語言的人核對。情緒比較則保留文字和角色，只改中性／急迫設定，檢查否定詞、金額及停頓是否清楚。

本組的文字欄位只是測試清單，不能據此聲稱台語自然度或情緒表達已通過。
:::

## 怎麼用、怎麼判讀

先把用途對應到來源、音色與交付檢查，再比較服務是否合適。相同平台可支援不同用途，但每個用途的驗收條件仍要分開寫。

### 換個場景

六類用途都要確認來源與音色。以下平台或模型是指引的例子，並非唯一選擇，也不表示服務底層必定採用指定架構。

| 場景 | 指引舉例 | 來源與音色 | 交付檢查 |
|---|---|---|---|
| 語音教材 | Google Cloud TTS | 課程稿、旁白音色 | 專名發音與章節 |
| 有聲書 | Amazon Polly | 書稿、朗讀音色 | 長段停頓與音色一致性 |
| 遊戲角色 | ElevenLabs | 對白、角色音色使用權 | 情緒與角色連續性 |
| 虛擬偶像、動畫配音 | VITS | 對白、角色音色使用權 | 獨特音色與口型需求 |
| 語音客服 | Microsoft Azure TTS | 業務稿、品牌音色 | 數字、條款與即時回應 |
| 智慧家居 | Google Cloud TTS | 指令回饋稿、裝置音色 | 回饋對應實際執行狀態 |

:::supplement[來源：Google Cloud Text-to-Speech basics；Microsoft Azure TTS 官方文件]
醫院候診要另查叫號隱私、姓名讀音與清晰度；交通站點則核對站名稿、多語音色及噪音中的方向與緊急語氣。

教材可事先產生完整音檔；客服可能需要邊生成邊播放。交付檔案、串流介面及錯誤回復方式要在測試前約定，避免把不同流程的延遲直接相比。
:::

## 常見誤解

- 「支援多語就是所有方言都自然。」指引把方言一致性列為挑戰，需要逐項驗收。
- 「公開訪談可以直接拿來複製音色。」可播放與可複製是不同的權利判斷。（補充）
- 「情感越強，任何場景都越好。」客服、警示與角色對白需要不同語氣。（補充）
- 「一個最好看的展示樣本就能選平台。」應以固定資料和一致端點比較。（補充）

## 小結

- 先列用途、語言、角色與整合需求，再比較平台。
- 教材、有聲書、角色、虛擬偶像、客服與家居各有交付重點。
- 情緒、多語與方言需要驗證，語音複製須確認來源與同意。
- 模擬數字只示範流程，正式方案還要取得聲音資產實測。（補充）
