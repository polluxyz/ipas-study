## 為什麼需要

兩張資料表想找出重複帳號，卻不希望直接展示原帳號。資料雜湊（Hashing）將輸入變成固定長度摘要，讓系統按摘要比對。

指引以 SHA-256 為例，但也提醒短 ID 容易被猜測。摘要看起來很長，不代表原輸入就難猜。

## 直覺

把每個候選代碼都交給同一台「摘要機」，同一輸入會得到同一輸出。測試者若已知只有 M01 到 M12，只需試這 12 種，就可能找出相符者。

## 定義與公式

密碼雜湊函數把任意長度輸入轉為固定長度摘要。單向性表示沒有設計成可用金鑰解密的逆運算；不表示別人無法猜一個輸入，再正向計算來核對。

:::supplement[來源：Python hashlib 官方文件]
SHA-256 的摘要是 256 位元，`hexdigest()` 用 64 個十六進位字元呈現。比對前須統一編碼及正規化規則；`M01` 與 `m01` 是不同輸入。
:::

| 技術 | 主要用途 | 回到原值的方式 |
|---|---|---|
| 資料遮蔽 | 減少可見資訊、保留部分格式 | 可能另查來源或由線索推測 |
| 資料雜湊 | 一致性比對、去重 | 無解密操作，但可試候選輸入 |
| 加密 | 保密且允許授權還原 | 持適當金鑰解密 |

## 走一次流程

### 步驟 1：固定輸入與轉換規則

共用資料的醫療代碼是 M01–M12，人資代碼是 R01–R12。皆用 UTF-8 編碼及 SHA-256，沒有鹽值或祕密金鑰；這個簡化設定專門展示猜測反例。

### 步驟 2：用完整摘要比對

M01 的完整摘要開頭是 `d968fce424f6`，R01 是 `e0a64b0b6d83`。這裡只縮短顯示，程式會用完整 64 字元摘要比對，不把顯示片段當成唯一鍵。

### 步驟 3：測試有限輸入空間

測試者依序生成 M01、M02，一直到 M12，各算一次摘要。這 12 個候選中，只有 M01 與目標摘要相符，證明本例的代碼仍可被猜出。

這不是破解雜湊演算法，而是原始候選太少。預先算好候選摘要再查表也是同類風險；換一個更長的摘要，並不會擴大原代碼集合。

指引另提醒「彩虹表攻擊（rainbow table）」這類利用預先計算的猜測風險。本例採逐一試算候選，沒有實作彩虹表；兩者都不能靠摘要很長就排除風險。

## 程式（補充）

以下對兩領域各核對一次完整摘要及候選搜尋，沒有處理真實帳號或連外查詢。

```python
from hashlib import sha256
def digest(value):
    return sha256(value.encode("utf-8")).hexdigest()
for prefix in ("M", "R"):
    target = digest(prefix + "01")
    candidates = [f"{prefix}{i:02}" for i in range(1, 13)]
    hits = [v for v in candidates if digest(v) == target]
    print(prefix, "長度", len(target), "顯示前綴", target[:12], "候選命中", hits)
print("同值一致", digest("M01") == digest("M01"))
print("大小寫不同", digest("M01") != digest("m01"))
```
```text
M 長度 64 顯示前綴 d968fce424f6 候選命中 ['M01']
R 長度 64 顯示前綴 e0a64b0b6d83 候選命中 ['R01']
同值一致 True
大小寫不同 True
```

:::tip[讀碼重點]
- 比對用 `digest(v) == target`，只有顯示才取前 12 字元。
- `range(1, 13)` 刻意列完本例已知的 12 種候選。
:::

## 怎麼用、怎麼判讀

適合用途包括使用者代碼比對、跨資料庫連結及資料去重。摘要本身不保留金額距離，不能把費用先雜湊，再用摘要平均數估計平均費用。

:::supplement[來源：NIST SP 800-188 第 4.3.1、4.3.2 節]
若處理可猜的識別碼，須另外評估受控鍵值轉換、隨機代碼及對照表管理。一般雜湊不能單獨提供匿名保證，其他準識別欄位也不會自動受到保護。
:::

### 換個場景

| 場景 | 想完成的事 | 判讀重點 |
|---|---|---|
| 使用者 ID、帳號、Email | 以摘要取代直接顯示 | 名稱叫匿名 ID 仍須測試可猜程度 |
| 跨資料庫比對、資料去重 | 用相同設定產生一致摘要 | 值域太小會暴露可連結性 |
| 醫療代碼（補充） | 連結受控資料中的同一代碼 | 12 種候選仍很容易試完 |
| 人資代碼（補充） | 合併同一員工的兩份紀錄 | 須評估猜測及跨表連結風險 |

## 常見誤解

- **單向就代表無法猜出原碼**：少量候選仍可逐一試算。
- **摘要相同就能完全證明身分相同**：比對依賴輸入品質，也有碰撞的理論可能。（補充）
- **雜湊能取代加密還原**：要授權取回原值，必須另外設計還原及存取機制。

## 進階

### 鹽值不等於祕密金鑰（補充）

鹽值會改變摘要，也會影響跨表一致性。即使加入公開鹽值，只有 12 種候選時仍能逐一試算；不要把「有加鹽」當成難以猜測的證明。

## 小結

- 相同輸入、編碼及設定可以一致比對摘要。
- 雜湊沒有解密操作，有限候選仍可被猜出。
- 比對與數值分析是不同需求。
- 受控回連、匿名效果與加密還原要分開評估。
