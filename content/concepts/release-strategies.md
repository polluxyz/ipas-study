## 為什麼需要

更新模型時，既有服務仍要繼續回應。指引建議以版本控管、滾動更新，並搭配藍綠或金絲雀部署，降低中斷及新版不穩定的風險。

發布策略（Release Strategy）決定新舊版本如何並存與接手。它處理更新過程，不代替模型品質驗證。

## 直覺

先看舊版與新版放在哪裡，再看使用者流量走向。指引列出三種策略，下圖與後文展開其基本作法。

![三種更新都保留新舊版本的過渡安排，請分辨切換環境、分流和替換副本。](figure:l21302-release-strategies-layout)

## 定義與公式

指引列出三種策略，並說明滾動更新要在維持服務時更新容器版本。下表將名稱與作法並列；藍綠、金絲雀的流程與分批副本細節為補充。

| 策略 | 基本作法 | 主要控制點 |
|---|---|---|
| 藍綠（Blue-Green，補充） | 新舊完整環境並存，再切換入口 | 環境切換 |
| 金絲雀（Canary，補充） | 先讓少量使用者接觸新版 | 新版影響範圍 |
| 滾動更新（Rolling Update） | 維持服務並更新容器版本 | 服務可用性 |

:::supplement[來源：AWS 藍綠白皮書；Google SRE「Canarying Releases」；Kubernetes「Deployments」]
三者可以組合。例如先準備綠環境，再將少量流量導向它。藍綠通常需要額外環境容量；金絲雀需要分流與分版本觀測；滾動更新期間則必須允許新舊版共存。

滾動更新可分批以新版副本替換舊版。副本是提供服務的執行實例；替換 1／20 個副本，不保證恰好 5% 請求進入新版，還要看路由、負載與連線行為。
:::

## 走一次流程

版本更新先保留可辨識的新舊模型，再逐步接手服務。目的都是讓更新過程仍可觀察、可控制，避免直接覆蓋唯一的正式版本。

### 同一個 rec-v3，換三種安排（補充）

共用 `L21302-D-releases.json`，舊版 rec-v2、新版 rec-v3 都使用 API v1 與特徵規則 f1。以下是替代方案，不代表三種發布已真的執行。

1. **藍綠**：藍環境留 rec-v2，綠環境載入已驗證 rec-v3；測試綠環境後切換入口，暫留藍環境作回復點。
2. **金絲雀**：路由先給 rec-v3 5% 請求，rec-v2 留 95%；觀察新版延遲、錯誤與品質，再決定擴量。
3. **滾動**：逐批替換服務副本，每批確認可用性；在新舊共存期間維持 API 與特徵格式相容。

金絲雀在 5% 下合格，不代表 100% 負載也合格。rec-v3 的教學紀錄在全面承接時 p95 升到 160 ms，因此擴量仍需重新過門檻。

## 怎麼用、怎麼判讀

指引場景是持續營運中的模型更新，要降低服務中斷與部署風險。先釐清團隊要驗證的是環境、少量真實使用者結果，還是分批替換的可用性。

### 影子輸出給誰看？（補充）

影子部署（Shadow Deployment）把正式請求複製給新版運行，但回給使用者的仍是舊版結果。它適合檢查延遲與輸出差異；不能直接得到新推薦的真實點擊率（CTR）。

![影子的新版輸出停在觀測紀錄，金絲雀的新版輸出則真正回給被分流的使用者。](figure:l21302-release-strategies-shadow-canary)

| 策略 | 使用者看到新版？ | 回復方式與條件 |
|---|---|---|
| 影子 | 否 | 停止鏡像；隔離寫入等副作用 |
| 金絲雀 | 少量使用者會 | 路由切回舊版，舊版須可用 |
| 藍綠 | 切換後會 | 切回保留環境，資料仍須相容 |
| 滾動 | 過渡期可能會 | 逐批恢復舊版，保留產物與容量 |

上述比較是補充內容。需要比較業務成效時，金絲雀分流也不自動等於嚴謹 A/B 實驗；還要控制分組、曝光與觀察時間，才能判斷改善原因。

### 換個場景

| 場景 | 想降低的風險 | 策略選擇線索 |
|---|---|---|
| 指引：持續營運的模型更新 | 中斷與新版不穩定 | 藍綠、金絲雀或滾動 |
| 零售推薦（補充） | 新推薦傷害真實點擊 | 小流量真實曝光與分版監控 |
| 製造檢驗（補充） | 多裝置同時更新失敗 | 分批替換，維持輸入相容 |
| 客服分類（補充） | 新版輸出格式異常 | 先影子觀測，再安排真實分流 |

## 常見誤解

- **「更新只要蓋掉舊權重。」** 保留版本與過渡安排才能降低服務風險。
- **「金絲雀通過就不必再看負載。」** 後續擴量仍可能出現延遲與資源瓶頸。（補充）
- **「影子能量到新推薦點擊。」** 使用者沒看見新版輸出，就沒有它的真實點擊。（補充）
- **「切回模型就能撤銷所有改動。」** 已寫入的資料與業務動作，可能需要另外補償。（補充）

## 進階

### 回復前的相容檢查（補充）

模型、前處理、API、資料庫及路由要有相容路徑。若新版刪了舊版必需的欄位，保留舊權重仍無法回復；應先演練整個服務組合的恢復。

## 小結

- 三種策略都用於降低持續更新的部署風險。
- 藍綠切換環境，金絲雀控制初期流量，滾動逐批替換副本。
- 影子結果不給使用者，無法直接衡量新版真實點擊。（補充）
- 回復依賴舊版可用與新舊資料、介面相容。（補充）
