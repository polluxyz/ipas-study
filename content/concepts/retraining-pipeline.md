## 為什麼需要

模型上線後仍需回收錯誤案例、重新評估及維護標註品質。重訓管線（Retraining Pipeline）把這些工作串起來，讓每次更新有來源、有檢查點，也有回復路徑。

啟動重訓和替換版本是兩件事。門檻警報可能需要修資料、修服務，或改用已驗證舊版；不必每次都重新訓練。

## 直覺

把警報當作工作單入口：先定位，再決定補資料、補標註或改模型。資料尚有疑點時就卡在檢查點，不把錯誤一路自動傳到正式服務。

![警報先進資料與環境檢查，再經標註、訓練及候選驗證；品質未過先停，發布後異常則走可回復路徑。](figure:l21302-retraining-pipeline-workflow)

## 定義與公式

本頁沒有固定計算公式，重點是每個階段的輸入、輸出及停止條件。

| 階段 | 主要產物 | 檢查點 |
|---|---|---|
| 監控回饋 | 警報與錯誤案例 | 是否需要修管線或模型 |
| 資料及標註更新 | 更新的學習素材 | 漂移、標註品質 |
| 訓練與驗證 | 固定候選及成績 | 是否達到更新條件 |
| 版本替換 | 熱更新或滾動釋出 | 舊版及容錯可用 |
| 追溯紀錄（補充） | 資料、標註、程式及產物指紋 | 可重現與可回復 |

熱更新（Hot Swap）強調在運行中切換模型；滾動更新逐批替換執行個體。方法不同，都需要相容性與品質驗證；不能把「可切換」當成「切換後必定更好」。

## 走一次流程

### 先判斷修什麼

指引建議由門檻啟動重訓，或替換已準備的模型版本；環境漂移時也要更新標註品質。

:::supplement[來源：本組合成資料 L21302-E；Google Cloud MLOps架構]
本組用視覺四期資料把不同處置分開：

| 觀測窗 | 觀察 | 處置 |
|---|---|---|
| W0 | 模糊20／1000、長尾錯5／50 | 固定參考與版本 |
| W1 | 模糊180／1000、光源偏暗 | 先修光源、鏡頭及輸入 |
| W2 | 模糊20／1000、長尾錯15／50 | 補少見材質真值，查候選需求 |
| W3 | 新候選，長尾錯5／50 | 持續驗證，不單憑前後歸因 |

W2 亮度分布已恢復、PSI 為 0，長尾錯誤仍為 30%。不能用畫質修好取代品質評估；模型負責人與現場人員應確認少見材質是否缺資料，再安排補樣和訓練。
:::

### 資料回收與重標註

回收客服、銷售及使用者反映的錯誤案例，轉成模型優化素材。資料變動後也需重新檢查標註，不只增加筆數。

:::supplement[來源：本組教學標註盤點；Google ML Pipelines課程]
以下是本組具體品質關卡：

1. **凍結事件窗**：保留輸入、預測、事件ID、群體、模型及特徵版本。
2. **配對真值**：授信等到期結果，視覺做人工複驗；時間不合或缺ID者先隔離。
3. **覆核標註**：分歧交第二位標註者，記錄標註規則及版本，不讓模型自己當裁判。
4. **建立資料版**：保留正常與困難樣本，檢查代表性、重複及群體量；與獨立EV集隔離。
5. **訓練再驗證**：用固定切分與種子產生候選，連到再訓練驗證與版本晉升的守門表。

回收 1,200 筆素材，依序隔離 20 筆缺ID、30 筆時間錯配、50 筆標註未決，這三類不重疊。剩 1,100 筆進入可用資料池；未決者覆核後另成新資料版，不直接覆寫原標註。

這 1,100 筆是新增素材，還要依使用目的建立訓練及調參切分；它們不是本組候選的 EV-0001–EV-1000。沿用前置版本紀錄方式，保存來源與切分指紋。

回饋不是完整母體。只收客訴會過度集中失敗；授信未獲貸者也可能沒有可觀測到期結果。應保存回收範圍及未知狀態，補具代表性的樣本後再判讀。
:::

### 訓練、驗證與回復

指引的熱更新與滾動替換以控制服務風險為目的。候選須先通過驗證；若異常，按預定回復或容錯規則處理。

:::supplement[來源：Google Cloud MLOps架構，Metadata management；Google SRE Canarying Releases]
本組候選 B 通過後仍先小量發布。發布清單固定模型、API v1、f1及資料／標註版本；回復點保留原模型、相容規則與路由設定，不只一個舊權重檔。

觸發回復時，先停擴量，再確認舊產物與輸入格式相容，實際切換路由及載入。核對請求日誌中的模型指紋、延遲、服務失敗及成熟真值品質，保存失敗窗與處理紀錄。

若新舊版本都不適用當前暗光場域，先轉人工複驗或暫停自動放行。回復不能撤銷已發生的錯誤授信或放行動作，這些需要另外追蹤。
:::

## 怎麼用、怎麼判讀

把資料、標註、訓練及發布拆成有檢查點的階段。自動化可以減少重複工作，但品質未過就應停止該次流程，保留錯誤證據。

### 換個場景

| 場景 | 回收素材 | 品質關卡 |
|---|---|---|
| 客服或銷售回饋 | 誤答、錯誤案例 | 核對標註與業務規則 |
| 環境漂移資料 | 改變後的輸入 | 更新資料標註品質 |
| 視覺檢測（補充） | 暗光、少見材質 | 先修設備再複驗 |
| 授信（補充） | 成熟到期結果 | 時間配對、不可觀測者 |
| 醫療影像（補充） | 後續診斷與覆核 | 病人隔離、專家分歧 |

## 常見誤解

- 「漂移門檻超過就把原模型刪掉。」應保留版本及可回復路徑。
- 「重標註就是把預測貼回去。」那會自我強化錯誤，需可靠真值與覆核。（補充）
- 「回復只改登錄標籤。」執行中的載入、路由及相容性都要驗證。（補充）
- 「重訓成功就是品質成功。」流程完成與候選合格是不同結果。（補充）

## 進階

### 失敗後從哪裡重跑（補充）

依固定輸入版本與階段產物定位失敗點。標註規則改過就重建受影響資料及候選，不能只重跑發布；模型產物未變、只是路由失敗時則查交付步驟，避免無謂重訓。

## 小結

- 警報先調查原因，再選擇修管線、重訓或替換版本。
- 資料回收與重標註要有品質關卡，之後才產生新候選。
- 候選驗證、正式發布與版本回復是分開的步驟。
- 保留來源及切分紀錄，回復後確認實際服務結果。（補充）
