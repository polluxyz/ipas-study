## 為什麼需要

找出公司、人名與案件，只得到一份名單。要知道哪家公司提出哪個案件，還需要辨認實體之間的關係。

關係抽取（英文：Relation Extraction）把非結構化文件中的關聯整理出來，可用於建立知識圖譜。指引舉公司與負責人、藥品與療效等應用。

## 直覺

「晴川法院受理星禾公司提出的甲案」包含三個實體。受理把法院連到甲案，提出把公司連到甲案；箭頭方向改了，句子的意思也變了。

![兩條箭頭都指向甲案：法院受理，公司提出；不要因三個節點同時出現就補上其他關係。](figure:l21101-relation-extraction-triples)

圖為教學示意。命名實體辨識先找到節點，關係抽取才判斷哪些節點之間有什麼連線。

## 定義與公式

關係抽取辨認已知實體之間的關聯，將文字變成可分析的結構。知識圖譜把實體及關聯連成網絡，方便整合與查詢。

### 三元組與方向（補充）

本組用「主體、關係、客體」三元組表示一條有向關聯。例如「晴川法院、受理、甲案」：主體是發出動作的法院，客體是被受理的案件。

這是三元組形式的教學輸出，不等於已建立完整RDF資料庫。每條另存原文證據識別碼，才能追查這個關係從哪段文字得到。

## 走一次流程

沿用NER頁的同一段法律L01及醫療行政M01，保持相同實體ID與原文位置。不要另編一組名稱，否則後面的關係可能接不到正確節點。

### 法律L01

| 原文實體 | NER類型 | 關係角色 |
|---|---|---|
| 晴川法院 | COURT | 受理的主體 |
| 星禾公司 | ORG | 提出的主體 |
| 甲案 | CASE | 兩條關係的客體 |

1. 取得三段實體，從「受理」「提出」判斷彼此的關聯。
2. 核對角色，得到「法院、受理、甲案」與「公司、提出、甲案」。
3. 不新增「公司僱用法院」之類無來源的邊。
4. 匯入圖譜前再次確認實體ID及關係方向，並保存L01作證據；同名不代表同一實體。（補充）

M01只支持「林安、掛號於、青禾醫院」，不支持「林安、任職於、青禾醫院」。地點相同不是職業關係證據。

### 共現、否定與未確定

M05說「林安與周晴在青禾醫院等候」，沒有交代兩人是親屬或同事。共現只表示可能值得檢查，不表示關係已成立。

L02「尚未委任」是否定，L05「可能委任」是未確定；兩者都沒有提供委任已成立的證據。

:::supplement[來源：NLTK Book第7章第6節；本組關係契約]
本資料不把兩者存成已成立委任，另存候選與原因；沒有輸出邊也不等於現實中永遠不會有關係。
:::

## 程式（補充）

以下程式讀取人工三元組並核對兩端ID，沒有自動理解動詞。輸出的JSON只是格式檢查；語意證據仍要回原句確認。

```python
import json, os
from pathlib import Path
root = Path(os.environ.get("IPAS_REPO_ROOT", "."))
d = json.loads((root / "content/examples/L21101-E-service-documents.json").read_text(encoding="utf-8"))
for r in d["documents"]:
    names = {e["id"]: e["text"] for e in r["entities"]}
    for t in r["triples"]:
        assert t["subject"] in names and t["object"] in names
        assert t["evidence_id"] == r["id"]
        if r["id"] == "L01":
            out = [names[t["subject"]], t["predicate"], names[t["object"]]]
            print(json.dumps(out, ensure_ascii=False))
    if r["id"] in {"L02", "L05"}:
        print(r["id"], "已確認關係:", len(r["triples"]))
```
```text
["晴川法院", "受理", "甲案"]
["星禾公司", "提出", "甲案"]
L02 已確認關係: 0
L05 已確認關係: 0
```

:::tip[讀碼重點]
ID存在與JSON格式正確，只能證明資料結構可接上。程式不會因為檢查通過，就證明「受理」方向、否定範圍或原文事實正確。
:::

## 怎麼用、怎麼判讀

從大量文件找公司與負責人、藥品與療效，可整理成圖譜供分析。任務要先定義關係種類，並核對文字實際支持哪種連線。

### 驗收分三層（補充）

先驗實體邊界與類型，再驗關係名稱、方向與是否成立，最後驗來源可追溯。三元組看起來完整，不表示三層都正確。

藥品與療效是指引列的應用，不表示文字一提到兩者就能證明治療效果。需要相應證據與領域覆核；本組實測只用行政與法律合成資料。

### 換個場景

| 場景或資料條件 | 關係用途 | 判讀重點 |
|---|---|---|
| 企業文件或資料庫 | 公司與負責人 | 名稱及關係證據 |
| 藥品相關文字 | 藥品與療效關聯 | 不由共現宣稱效果 |
| 大量非結構化文件 | 組成知識圖譜 | 實體一致與關係方向 |
| 醫療行政（補充） | 人物與掛號機構 | 掛號不代表任職 |
| 法律案件（補充） | 法院受理、公司提出案件 | 否定與未確定分開存 |

## 常見誤解

- 「NER已找到兩個實體，就知道它們有關係。」節點與連線是不同輸出。
- 「同句、相鄰就表示關係成立。」共現沒有提供關係種類與方向。
- 「把尚未刪掉更容易建圖。」這會把否定改成肯定事實。
- 「JSON可解析就代表抽取正確。」格式驗證無法代替語意覆核。（補充）

## 進階

### 圖譜的身分一致性（補充）

合併多份文件時，兩個「林安」未必同人，同一組織也可能有不同簡稱。三元組要連到穩定識別碼，不能只以顯示名稱合併。

本例刻意使用文件內ID，不冒充跨文件實體解析。若要建立全域節點，還需另做同名辨識與來源衝突處理。

## 小結

- 實體是節點，關係說明節點如何相連。
- 三元組須保留方向與來源，不能由共現直接補邊。（補充）
- 否定與未確定不當作已成立關係；格式與語意分開驗收。（補充）
