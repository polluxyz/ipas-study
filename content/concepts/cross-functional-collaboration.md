## 為什麼需要

業務以為「提示」代表轉人工，IT 卻實作成自動處置，模型再準也可能無法使用。跨部門協作要先避免這種需求語意的落差。

指引把資訊不透明、管道不足與責任不清列為組織風險。工作做完才發現彼此期待不同，會浪費資源並延誤交付。

## 直覺

同一項任務要同時有「誰負責」「大家去哪裡看」「什麼時候確認」三個答案。只有聊天室或每週會議，都不會自動產生清楚責任。

## 定義與公式

| 機制 | 要回答的問題 | 實際紀錄 |
|---|---|---|
| 責任範圍 | 資料、驗收、整合各由誰承接 | 主責及部門分工 |
| 同步節奏 | 阻礙何時被發現與處理 | 例會、進度報告與待辦 |
| 共用平台 | 哪裡能找到同一版資料 | 任務看板、文件及溝通管道 |

指引建議定期同步，常見做法是每週例會。看板管理任務，共用文件保存規劃與版本，通訊工具協助快速討論，三者用途不同。

指引的任務看板例子有 Jira、Trello；共用文件例子有 Notion、Confluence；即時通訊例子有 Slack、Microsoft Teams。

先分清類型，再對到進度、文件與討論的用途。

:::supplement[來源：Atlassian「Roles and Responsibilities」；Google「Stakeholders」]
本例把主責、確認者與協作方分開。每個交付物至少有一位明確主責；同一人可以參與多項工作，但不能讓「大家負責」取代指定交付責任。
:::

## 走一次流程

### 製造案共用責任矩陣（補充）

以下直接使用共用 JSON 的 M1～M6。這張表也是兩個角色頁的交接依據；零售案 R1～R6 採相同角色規則。

| 任務 | 主責 | 確認者 | 交付物 |
|---|---|---|---|
| M1 範疇 | 專案負責人 | 主管 | 計畫 v1 |
| M2 資料 | 資料工程師 | 業務單位 | 資料與切分 v1 |
| M3 模型 | 模型開發者 | 技術部門 | 模型與實驗紀錄 v1 |
| M4 操作及規則 | 體驗設計兼業務顧問 | 業務單位 | 操作流程與規則 v1 |
| M5 整合 | 系統架構師 | 技術部門 | API 與部署說明 v1 |
| M6 驗收 | 測試工程師 | 主管 | 測試與審查紀錄 v1 |

### 需求到驗收的同一筆決議（補充）

1. 需求：業務在 M4 確認瑕疵提示後交由人員處理，本次不自動停線。
2. 設計：架構師在 M5 的 API 規格記錄「待覆核」狀態與模型版本，回報業務確認。
3. 同步：每週例會追蹤未結項；若處置語意變動，先更新共用規格，不只留在私訊。
4. 驗收：M6 用正常、不可判讀與逾時案例確認仍走約定的人工處理流程。
5. 決議：測試證據與業務確認連回 M4、M5；未解問題由指定主責於期限前關閉。

本例規定看板放狀態、主責和期限；文件放版本及驗收依據；通訊討論結束後，把決定回填文件。阻礙發生當日回報，不等下一週例會。

### 風控與 IT 的需求落差

指引的金融案例中，風控和 IT 溝通不足，模型開發與業務需求脫節。只追蹤「模型訓練完成」不足以避免此風險，還要確認模型接到哪個業務動作。

:::supplement[來源：Google「Stakeholders」的 Deliverables；Atlassian「Roles and Responsibilities」]
自編案例：風控要高風險交易轉人工，IT 卻實作成直接拒絕。這不是單純模型分數問題，而是沒有共同確認處置需求，也沒在驗收檢查完整流程。

三個控制點是：風控確認需求及例外；IT 回報對應規則與實作版本；雙方用同一批情境驗收處置結果。任何一方改規則，都要回到這三點重新核對。
:::

## 怎麼用、怎麼判讀

看進度報告時，不只看百分比。要能找到下一個交付對象、未結問題及誰有權作決定；否則「完成 90%」仍可能卡在部門交界。

### 換個場景

下表先列指引的部門與金融案例，再換到其他需要共同驗收的服務。

| 場景 | 協作重點 |
|---|---|
| IT、業務、法務、資料多部門導入 | 釐清資料提供、模型驗收與系統整合責任 |
| 金融風控與 IT 目標不一致 | 需求確認、回報及驗收對照業務動作 |
| 零售推薦（補充） | 庫存規則變更要同步模型、介面及測試 |
| 醫療分診（補充） | 臨床與 IT 一起確認轉人工及例外處理 |
| 交通告警（補充） | 交通單位與維運一起確認值班及處置流程 |

## 常見誤解

- 「買了協作工具就有協作」：工具仍需要清楚責任與使用規則。
- 「會議越多，資訊就越透明」：還要能找到版本及決議。（補充）
- 「模型指標達標就能落地」：業務處置與整合需求也要一致。
- 「跨部門任務就交給大家」：沒有主責，交界最容易漏接。（補充）

## 進階

### 升級也要有對象（補充）

若資料主責與業務無法就驗收定義達成一致，記錄仍有分歧的條件與選項，交由有決策權者處理。不能靠先改程式，讓未決需求看起來已經定案。

## 小結

- 責任範圍、同步節奏與共用平台要一起建立。
- 看板、文件及通訊各承接不同工作。
- 需求確認、實作回報及流程驗收能減少部門落差。（補充）
- 決議需有主責、版本與追蹤期限。（補充）
