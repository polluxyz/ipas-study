## 為什麼需要

模型會預測，仍可能讓使用者不知道怎麼操作，也可能接不上既有系統。體驗設計、業務顧問、架構與測試各補上一段交付責任。

這些工作不必等模型完成才開始。業務指標、操作情境與部署限制，會反過來影響模型應達到什麼要求。

## 直覺

把同一個輸出交給四個角色看：使用者看得懂嗎、符合業務規則嗎、系統接得上嗎、在指定條件下驗證過嗎。四個答案都要有證據。

![從體驗設計兼業務顧問、系統架構師與測試工程師三條泳道，找出操作、部署與測試的交付物。](figure:l21202-ai-project-roles-responsibility-lanes)

## 定義與公式

| 角色 | 主要問題 | 工作產物 |
|---|---|---|
| UI/UX 設計師 | 使用者怎麼理解及操作 | 畫面與使用流程 |
| 業務顧問 | 要解決什麼問題、用何種指標 | 業務目標、指標及需求 |
| 系統架構師 | 如何整合至現有環境 | 伺服器、資料流、API 與部署設計 |
| 測試工程師 | 品質與穩定性是否符合要求 | 模型驗證、壓測及缺陷回報 |

UI 是使用者介面（User Interface），UX 是使用者體驗（User Experience），用來安排操作畫面及使用流程。

應用程式介面（API，Application Programming Interface）供系統交換資料，不等於操作畫面。

指引以 AWS Lambda 作為系統架構師需熟悉的雲端服務例子。

:::supplement[來源：AWS「What is AWS Lambda?」；Google「Assembling an ML team」；「Stakeholders」]
AWS Lambda 是執行程式的無伺服器運算服務，基礎伺服器的配置與管理由服務方處理。

本例同一人兼任設計師與顧問，仍將「庫存規則由誰確認」與「無結果時畫面怎麼呈現」分開記錄。兼任是人力安排，不能讓責任消失。
:::

## 走一次流程

### 先對齊使用流程與規則（補充）

共用製造案的 M4 由體驗設計兼業務顧問交付「操作流程與規則 v1」。操作是「影像進來 → 顯示瑕疵提示 → 現場人員覆核 → 記錄處置」；規則是「只提示、不直接停線」。

換到零售 R4，操作是「進入商品頁 → 看推薦 → 點選商品」；缺貨商品不得進入推薦，無結果改顯示熱門品。業務顧問確認規則，設計師安排正常及例外狀態。

### 再把需求落到系統

指引的製造案例以地端伺服器兼顧安全與低延遲。架構師要從資料如何進入、模型在哪裡運行，一路設計到結果如何回到既有系統。

![上半部交付模型，下半部由輸入經 API 到推論及操作端；請分開看模型交接與線上資料路徑。](figure:l21202-compute-resource-planning-training-serving)

:::supplement[來源：Google Cloud「Best practices for implementing machine learning」的 Model deployment and serving]
本例 M5 選地端 API 與 CPU 推論節點，影像不出廠。50 ms 的要求要覆蓋輸入、前處理、模型和回應，不能只測模型呼叫；節點數與分段預算見算力與訓練推論資源配置。

R5 可使用通過用途審查的雲端 CPU 服務，但必須交代特徵更新、逾時回應與版本。換成雲端不會自動免除資料限制，也不保證回應更快。
:::

### 最後列測試責任與門檻

:::supplement[來源：本組共用教學資料；Google「Stakeholders」的 Deliverables]

M6、R6 各安排 32 人時，由測試工程師主責；遇到模型或介接缺陷，再交給模型開發者或架構師修正。下表是計畫中的通過標準，並未真的啟動服務壓測。

| 測試面向 | 製造門檻 | 零售門檻 | 修正配合者 |
|---|---|---|---|
| 功能 | 20 筆合法輸入皆回傳約定格式 | 20 筆合法輸入皆符合格式及缺貨規則 | 架構師、顧問 |
| 模型品質 | 100 件瑕疵至少檢出 95 件 | 100 次請求至少 68 次前五名命中 | 模型開發者 |
| 壓力 | 25 次／秒、15 分鐘；p95 ≤50 ms | 60 次／秒、15 分鐘；p95 ≤120 ms | 架構師 |
| 噪聲／異常 | 10 張不可判讀影像皆轉人工 | 10 筆格式錯誤請求皆拒絕且不當機 | 模型與架構角色 |

兩案壓測另要求錯誤比例不超過 1%。p95 是 95% 請求不超過的回應時間；要量完整請求，不能將不同請求各段的 p95 直接相加。

不可判讀影像轉人工，是本案的例外處理門檻，不表示模型能在所有噪聲下保持原分數。
:::

指引以客服語音受噪音影響提醒：應測實際環境，將問題回饋調整。

## 怎麼用、怎麼判讀

看到延遲問題，先沿資料流定位，再安排架構或模型角色修正。看到使用者誤解輸出，先檢查操作與業務定義，不能一律歸因於模型不準。

### 換個場景

從指引的介面、銷售、製造與客服案例，看四類角色如何回應不同需求。

| 場景 | 角色關注 |
|---|---|
| AI 客服操作介面 | 設計師讓業務人員容易上手 |
| 銷售預測 | 業務顧問確認關鍵指標 |
| 製造地端部署 | 架構師兼顧資料安全與延遲 |
| 高流量、客服語音有噪音 | 測試工程師壓測並回饋干擾問題 |
| 醫療提示畫面（補充） | 顯示待覆核狀態並測例外操作 |
| 交通異常告警（補充） | 測尖峰告警及失敗轉人工 |

## 常見誤解

- 「UX 只管美觀」：也要安排使用流程，讓操作可理解。
- 「架構師只選雲端品牌」：還要設計資料流、介面及部署。
- 「模型分數高就不用測系統」：負載與異常輸入可能另有問題。
- 「測試工程師負責驗證，因此所有缺陷都由他修」：修正回到對應工作角色。（補充）

## 進階

### 品質門檻與簽核權分開（補充）

測試工程師整理結果與未解問題，業務及有權責的審查者決定是否符合進場條件。某一項測試通過，不能代替對整體範疇與風險的核准。

## 小結

- 設計師關注操作，顧問確認業務目標與指標。
- 架構師設計資料流、API 及部署。
- 測試工程師驗證模型品質與系統穩定性。
- 自編測試門檻需分開記錄品質、負載與異常條件。（補充）
