## 為什麼需要

一張訂單被系統重送三次，並不代表顧客買了三次。若每份副本都進入訓練，這張訂單的特徵就被放大，統計總額也會偏高。

重複資料檢查要和格式統一一起做。同一質量以公克或公斤記錄、同一類別有不同寫法，都可能讓副本看起來不相同。

科1指引把重複與主鍵衝突列在「唯一性」，把欄位間邏輯是否合理列在「一致性」。科3另談單位與格式一致；判讀時要分清檢查的是哪一層。

## 直覺

先問「一列代表什麼」，再問「兩列是不是同一次觀測」。顧客表的一列可代表一位顧客；交易表的一列則可能代表一張訂單，不能用相同的去重鍵。

主鍵（Primary Key）用來識別觀察單位。沒有可靠主鍵時，可用時間、來源與欄位相似度找候選，再確認是否為重複。

:::caution[注意]
同一顧客再次下單、同一機台隔一小時再次量測，都可能是合法的新事件。數值一樣也不代表應刪除。
:::

## 走一次流程

### 先看事件，再看欄位

共用快照`L23301-B-cleaning.json`每域32筆，沿用前置組索引。下表取零售28、30、31、29列；`row_id`識別匯入列，`event_id`識別訂單。

| 索引／訂單 | 顧客 | 原始金額／類別 | 來源判斷 |
|---|---|---|---|
| 28／R29 | 顧客08 | `450`／`A` | 首次入庫 |
| 30／R29 | 顧客08 | `450`／`A` | 完全重送 |
| 31／R29 | 顧客08 | ` 450.0 `／`a` | 格式不同的重送 |
| 29／R30 | 顧客08 | `650`／`B` | 合法的另一張訂單 |

1. 宣告一列代表一張訂單，檢查訂單鍵是否缺漏。
2. 將金額轉成數值，類別依既定對照表統一；450與450.0表示相同金額。
3. 以訂單鍵找同鍵列，再回看內容與重送日誌。
4. 已確認R29為重送，留下索引28；R30仍保留。
5. 記錄被合併的原始索引與保留依據，方便追查。

:::supplement[來源：pandas Indexing and selecting data：Duplicate data]
四列若只對業務欄位做原始整列去重，會剩三列；格式統一後剩兩列。若連唯一的`row_id`一起比較，每列都不同，根本刪不到副本。

若同張訂單原本就可有多個商品明細，主鍵要包含明細編號。若同鍵金額不一致，先查版本或衝突，不能任意保留第一列。
:::

### 統一單位與欄位值

製造快照的質量欄交替記為2500公克與2.5公斤，統一為2.5公斤後才比較。類別`A`與`a`在本例對照表代表同類；指引舉的`male`與「男」也須依欄位定義對照。

主資料的兩份副本都在驗證區內；去重後，每域從32列變30列，保留原索引。切分仍是原訓練索引0–23與原驗證索引24–31，驗證實際留下6列。（切分規則為補充。）

## 程式

### 從原始整列比較到主鍵去重（補充）

下列四筆就是上表的業務欄位，不包含唯一匯入列號。`keep="first"`的前提是已由來源確認保留第一份；它本身不會驗證資料正確性。

```python
import pandas as pd
df = pd.DataFrame({
    "event": ["R29", "R29", "R29", "R30"],
    "customer": ["顧客08"] * 4,
    "amount": ["450", "450", " 450.0 ", "650"],
    "category": ["A", "A", "a", "B"],
})
print(len(df.drop_duplicates()))
df["amount"] = pd.to_numeric(df["amount"].str.strip())
df["category"] = df["category"].str.upper()
print(df.duplicated(subset=["event"]).tolist())
clean = df.drop_duplicates(subset=["event"], keep="first")
print(len(df.drop_duplicates()), clean["event"].tolist())
```
```text
3
[False, True, True, False]
2 ['R29', 'R30']
```

:::tip[讀碼重點]
`subset`決定比較哪些欄；省略時比較全部資料欄。`keep=False`會把整組重複都移除，不是每組留一列。
:::

## 怎麼用、怎麼判讀

先固定觀察單位，再制定去重與衝突處理規則。主鍵缺漏、鍵值重用或多來源版本衝突，都值得另列清單，不能把去重當作正確性保證。

### 套件名稱分開看

| 套件 | 常用寫法 | 比較範圍 |
|---|---|---|
| pandas | `df.drop_duplicates(subset=["event"])` | 指定資料欄；預設全部資料欄 |
| PySpark | `df.dropDuplicates(["event"])` | 指定資料欄；預設全部資料欄 |

:::supplement[來源：pandas DataFrame.drop_duplicates；PySpark DataFrame.dropDuplicates]
Spark也有`drop_duplicates()`別名，但兩套介面不能混用參數。pandas有`keep`，上述Spark方法沒有。

Spark的API未承諾同鍵列保留哪一列，不能按輸入次序推定。若要保留最新版本，須按事件鍵分組，再依版本及唯一的決勝欄位排序選取。
:::

### 換個場景

| 場景／資料條件 | 判讀重點 | 處理依據 |
|---|---|---|
| 顧客或交易主鍵重複 | 先確認顧客表還是交易表 | 科1指引的主鍵檢查 |
| 系統重寫或資料整合重複 | 相同觀察是否被重複加權 | 科3指引的觀察單位 |
| 公克／公斤與類別寫法不同 | 先統一意義再比較 | 單位及欄位對照表 |
| 醫療回診（補充） | 同病人不同就診不可合併 | 病人及就診事件鍵 |
| 交通刷卡（補充） | 短時間多次刷卡也可能合法 | 車次、事件與設備日誌 |

## 常見誤解

- **顧客編號相同就只留一次。** 要看一列代表顧客、訂單還是明細。
- **整列不同就不重複。** 單位、大小寫或版本差異都可能讓同一事件看似不同。
- **去重能自動修正衝突。** 保留某列前仍要確認資料來源與欄位含義。

## 進階

### 跨切分的副本（補充）

若同一事件的副本跨到訓練與驗證區，應先把副本歸成同一事件再切分，避免資料洩漏。這和按顧客切群是不同層次：新事件即使合法，仍可能需要群組切分。

## 小結

- 先宣告觀察單位，才知道主鍵要選哪幾欄。
- 同一顧客的新交易可合法保留，已確認的重送才合併。
- 單位與類別寫法統一後，再查近似重複及衝突。
- 去重參數與保留紀錄要一起留下，才能還原處理過程。
