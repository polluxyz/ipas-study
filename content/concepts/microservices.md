## 為什麼需要

零售系統同時做特徵查詢、模型推論與促銷。若全部包成一個共同發布的應用，更新模型或增加推論資源時，其他功能也可能要跟著一起調整。

微服務架構（Microservices）把應用拆成一組責任較清楚的小型服務。各服務可以獨立更新與擴展，適合多團隊協作及不同模組需求差異較大的情況。

## 直覺

先看「能不能各自發布與配置資源」，比只看服務數量更有意義。推論服務升級時，企業流程服務仍能使用相容的 API，就不必同時改版。

![單體一起發布，微服務按責任分開發布；服務之間仍有 API 或事件依賴。](figure:l21302-microservices-boundaries)

## 定義與公式

指引強調每個服務實作單一功能，並能獨立部署、更新與擴展。這帶來彈性，也要求標準化的介面與分散式管理能力。設計得當時，也能將錯誤限制在局部服務，讓其他功能繼續運作。

| 面向 | 單體應用 | 微服務 |
|---|---|---|
| 發布邊界 | 共同驗證及發布 | 可按服務獨立更新 |
| 資源擴展 | 常以整個應用為單位 | 按模組需求擴展 |
| 團隊協作 | 共同發布節奏 | 可分工並行開發 |
| 介接管理 | 程序內呼叫較多 | 要管理跨服務 API |
| 維運成本 | 較少網路邊界 | 分散式追蹤與協調較複雜 |

:::supplement[來源：Microsoft Learn「Microservices architecture style」的 Fault isolation、Challenges]
「獨立部署」還需要介面相容與責任界線；如果每次改版都要所有服務同步更新，就沒有真正取得這個好處。

指引說單一模組失效不影響全系統，應理解為設計目標。若上游無限等待下游，或服務共用同一個失效資源，故障仍可能擴散。
:::

## 走一次流程

### 拆分零售與製造服務

推論流量增加時，可單獨擴增模型 API 模組；不同團隊也能各自更新負責的服務。各模組仍須用標準 API 串接。

:::supplement[來源：Microsoft Learn「Microservices architecture style」「Design patterns for microservices」；教學合成資料 L21302-A]
沿用 `L21302-A-requests.json` 的 24 筆固定請求。可以把責任分成特徵服務、推論服務與企業流程服務，先讓介面與失敗處置各自清楚。

1. 特徵服務提供 f1 及更新時間，讓推論服務辨識 r07 的特徵已過期。
2. 推論服務依約定輸入回傳 rec-v2 或 inspect-v3 結果；更新權重時，先檢查輸出是否仍相容。
3. 企業流程服務接手 CRM 或 MES 動作，保留 request_id 與業務狀態。
4. r10／m10 下游逾時時，將工作標成待確認，不讓其他請求無限等待。

若推論流量增加，可只擴展推論服務。若瓶頸其實在特徵庫，新增推論副本可能讓特徵庫更忙，因此還要觀察完整依賴路徑。
:::

## 怎麼用、怎麼判讀

不同模組的更新頻率、負載與團隊責任差異越大，獨立服務越可能有價值。代價是介面、日誌、網路故障與版本相容都要一起管理。

### 換個場景

| 場景 | 拆分帶來的好處 | 要付的代價 |
|---|---|---|
| 指引：跨團隊並行開發 | 各模組可獨立更新 | 標準 API 與分散式管理 |
| 指引：推論流量增加 | 單獨增加模型 API 資源 | 管理服務間依賴 |
| 零售推薦（補充） | 模型改版與促銷流程分開 | CRM 逾時及狀態追蹤 |
| 製造檢驗（補充） | 模型更新與 MES 介接分開 | 檢驗與產線動作的一致性 |
| 物流平台（補充） | 預測與派車服務各自擴展 | 跨服務事件及重複動作 |

### 小系統不必急著拆（補充）

若只有一個小團隊、負載不大且更新節奏一致，模組清楚的單體可能更省管理成本。先確認獨立部署與擴展的需求，再決定拆分界線。

## 常見誤解

- **「每個服務都很小，就一定是好架構。」** 重要的是責任與介面清楚，過細拆分會增加呼叫成本。（補充）
- **「一個服務掛掉一定不影響其他服務。」** 還要處理逾時、同步等待與共用資源。（補充）
- **「只要用了容器就是微服務。」** 封裝方式與服務拆分是不同決策。（補充）
- **「拆分後不用共同規格。」** 服務間仍要有標準 API 與相容約定。

## 進階

### 故障隔離需要什麼（補充）

對每個遠端依賴設定等待上限，並準備有限重試、替代結果或非同步處理。用同一個 request_id 串起日誌，才找得到故障從哪個服務開始。

拆分服務後也要管理資料一致性。兩個服務各自完成一步，不代表整個企業作業已完成，仍需追蹤與補償未完成的動作。

## 小結

- 微服務讓不同責任可以獨立部署、更新與擴展。
- 介面標準與分散式管理能力是取得彈性的代價。
- 故障隔離要靠依賴處理，不能只靠程序拆開。（補充）
- 架構選擇應依團隊、負載與更新需求決定。（補充）
