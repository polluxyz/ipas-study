## 為什麼需要

監控發現效能下降或資料改變，可以啟動再訓練（Retraining），讓新資料進入模型更新流程。但新產物只是候選，仍要確認它是否值得替換現行版。

:::supplement[來源：Google Cloud MLOps架構，Data and model validation]
指引 4-42、4-43 的重訓成功案例不代表每次都會改善。若原因是錯誤資料、標註偏差或服務瓶頸，再訓練可能無效，甚至放大問題。
:::

## 直覺

觸發回答「是否開始做候選」，晉升回答「這個固定候選能否承接服務」。兩次決策分開，才不會把排程成功誤認為模型品質通過。

## 定義與公式

指引的自動再訓練由監控門檻觸發。候選驗證再加上獨立資料、同版產物及守門指標，具體門控屬補充。

### 候選門控（補充）

$$
r=\frac{e_{\mathrm{main}}+e_{\mathrm{tail}}}{n_{\mathrm{main}}+n_{\mathrm{tail}}},\qquad
r_g=\frac{e_g}{n_g}
$$

$e_g$ 是群體 $g$ 的錯誤數，$n_g$ 是其已配對真值樣本數，$r$ 是整體錯誤率，$r_g$ 是群內錯誤率。各分母須大於 0；錯誤率是單標籤分類準確率的補數。

另用群間最大差衡量本組兩群的錯誤率差：

$$
\Delta=\max_g r_g-\min_g r_g=\left|r_{\mathrm{tail}}-r_{\mathrm{main}}\right|
$$

$\Delta$ 是群差，差值以百分點解釋；最後一個等號限定只有一般群與長尾群。

這對應 Fairlearn `difference(method="between_groups")` 的最大值減最小值；10 百分點門檻是本組政策。

本例候選 B 的一般群為 24／950≈2.526%，長尾為 5／50＝10%；整體 29／1,000＝2.9%，群差約 7.474 個百分點。

本例群差與長尾上限是公平風險的操作性守門條件，不代表已證明完整公平性。群體定義、錯誤代價及樣本不確定性仍須另行審查。

## 走一次流程

### 何時觸發、誰接手

指引以電商推薦衰退說明監控觸發重訓；定期回收錯誤案例也可形成更新需求。觸發應連到負責人與處理紀錄，不能只有一個排程。

:::supplement[來源：Google Cloud MLOps架構，ML pipeline triggers；本組合成資料]
本組授信 W2 完整回收後錯誤率 5.8%，已超過 4% 的教學警戒線。資料工程師先排除缺值、單位和時戳錯配；模型負責人再決定啟動訓練，風險負責人決定是否先轉人工覆核。

W2 為 7/15–7/21，30 天延遲使真值於 8/14–8/20 才到齊。這是另一輪觸發示範；7/22 開始的 W3 B 版，來自下節較早的歷史資料及驗證，不使用 W2 真值。

PSI 警報可先啟動調查；標籤未成熟時只排資料回收，不把未標註資料當正確答案。定期更新也須通過同一套晉升門控。
:::

### 固定資料與候選（補充）

共用 JSON 的 TR 用於訓練、VA 用於調參，EV-0001–EV-1000 是未參與兩者的獨立門控集。每領域含一般群 950 筆、長尾 50 筆；同領域的現行版與三候選用同一批索引評分。

兩領域的 ID 各自命名，索引與切分規則相同，樣本與真值不同。歷史事件最晚 5/31，真值在 6/30 前齊備；以下驗證於 7/21 核准，才有 W3 的受控發布。

EV 與 W0–W3 的監控樣本分離。現行版 EV 計數刻意設成與各領域 W2 摘要相同，方便比較；這不表示驗證偷用了當時尚未成熟的 W2 真值。

所有候選固定種子 21302、API v1、f1；記錄資料、標註、程式及產物版本。下面是合成的驗證紀錄核算，不宣稱真的訓練了四個模型。

### 先訂門檻，再看結果（補充）

| 門控 | 授信教學條件 | 用意 |
|---|---|---|
| 整體品質 | 錯誤率≤4%，且優於現行 | 不接受整體退步 |
| 群體品質 | 長尾≤15%、群差≤10百分點 | 防止局部失準 |
| 證據量 | 真值到齊、長尾至少50筆 | 不把缺證據當通過 |
| 資源 | p95≤120ms、記憶體≤512MB | 避免部署後壅塞 |
| 相容與回復 | API及f1相容，舊版可用 | 保留可執行止損點 |

候選都在同一固定負載與環境做資源驗證。視覺改用 p95≤80 ms，品質門檻相同，但使用視覺自己的錯誤計數；授信與視覺的真值不可互換。

|---|---|---|---|
| 現行 | 58／1000＝5.8% | 20／50＝40% | 95ms；比較基準 |

| C | 20／1000＝2% | 2／50＝4% | 135ms；資源遭拒 |

視覺同樣比較現行版與三候選，長尾是預先定義的少見材質群：

| 版本 | 整體錯誤／分母 | 長尾錯誤／分母 | 視覺p95／判斷 |
|---|---|---|---|
| 現行 | 34／1000＝3.4% | 15／50＝30% | 60ms；比較基準 |
| A | 31／1000＝3.1% | 25／50＝50% | 65ms；群體遭拒 |

A 的整體改善不能抵銷長尾惡化。C 的品質最佳仍超過硬性延遲預算，不能直接上線。候選比較另應檢查統計不確定性；本表通過只代表符合教學規則。

### 核准後仍要線上驗證（補充）

模型與風險負責人審查 B 的報告，確認授信 credit-e-b／視覺 inspect-e-b 的固定產物。經模型登錄後，按漸進式部署與擴量門檻分 5%→30%→100% 觀察。

本組約定每階段至少 30 分鐘、1,000 次請求；品質還要等代表性真值。

延遲需改善時暫停擴量；若服務失敗率連續三個完整一分鐘窗大於 5%，依回復計畫止損。這是本組政策，不沿用前置發布資料的門檻。

成熟真值顯示長尾大於 15% 時也停止擴量並依約回復。回復需確認模型、特徵及API相容，再查流量與指標；安全事件不必等完整品質窗才處置。

## 程式（補充）

以下兩段接續執行，核算共用候選資料。第一段只保存已量得的教學紀錄，不進行訓練。

```python
rows = {
    "授信": [("current", 38, 20, 95, 320), ("A", 8, 30, 100, 350),
             ("B", 24, 5, 110, 400), ("C", 18, 2, 135, 480)],
    "視覺": [("current", 19, 15, 60, 320), ("A", 6, 25, 65, 350),
             ("B", 15, 4, 70, 400), ("C", 9, 1, 95, 480)]
}
for domain, records in rows.items():
    base = (records[0][1] + records[0][2]) / 1000
    print(f"{domain}現行整體錯誤率：{base:.1%}")
```
```text
授信現行整體錯誤率：5.8%
視覺現行整體錯誤率：3.4%
```

第二段用硬門檻的交集做決策。範例已確認 1,000 筆真值到齊、API／f1 相容；真實流程缺任何一項證據，都先暫停晉升。

```python
for domain, cap in [("授信", 120), ("視覺", 80)]:
    records = rows[domain]
    base = (records[0][1] + records[0][2]) / 1000
    for name, main_e, tail_e, delay, memory in records[1:]:
        total, tail = (main_e + tail_e) / 1000, tail_e / 50
        gap = abs(tail - main_e / 950)
        quality = total <= 0.04 and total < base and tail <= 0.15 and gap <= 0.10
        passed = quality and delay <= cap and memory <= 512
        print(f"{domain} {name}：錯誤{total:.1%} 長尾{tail:.1%} 群差{gap * 100:.3f}百分點 "
              + ("可送核准" if passed else "拒絕晉升"))
```
```text
授信 A：錯誤3.8% 長尾60.0% 群差59.158百分點 拒絕晉升
授信 B：錯誤2.9% 長尾10.0% 群差7.474百分點 可送核准
授信 C：錯誤2.0% 長尾4.0% 群差2.105百分點 拒絕晉升
視覺 A：錯誤3.1% 長尾50.0% 群差49.368百分點 拒絕晉升
視覺 B：錯誤1.9% 長尾8.0% 群差6.421百分點 可送核准
視覺 C：錯誤1.0% 長尾2.0% 群差1.053百分點 拒絕晉升
```

:::tip[讀碼重點]
`and` 表示每一項硬門檻都得通過。程式只產生核准建議，沒有改模型登錄、部署路由或現行版本。
:::

## 怎麼用、怎麼判讀

監控警報決定何時調查，驗證結果決定候選能否晉升。資料回收與重標註步驟見重訓、重標註與版本回復，本頁集中在候選比較和上線決策。

### 換個場景

| 場景 | 觸發線索 | 候選驗證重點 |
|---|---|---|
| 電商推薦 | 推薦準確率下降 | 更新後重新評估 |
| 授信（補充） | 成熟真值的長尾錯誤增加 | 群體品質、到期資料 |
| 視覺檢測（補充） | 人工複驗顯示少見材質失準 | 材質分群、現場延遲 |
| 客服分類（補充） | 新產品意圖誤轉增加 | 新舊意圖都不可退步 |

## 常見誤解

- 「自動觸發等於自動發布。」指引也要求測試門檻，候選仍要通過驗證。
- 「重訓完成就會回到原準確率。」成功案例不能當保證。（補充）
- 「整體最好就是最佳候選。」群體與資源硬門檻仍可能拒絕它。（補充）
- 「同一獨立集可以一直拿來調參。」反覆選擇會使它失去獨立性。（補充）

## 進階

### 評估資料被看過後（補充）

EV 集用來比較這批候選後，團隊已知道它的結果。若據此再修改特徵或超參數，下一輪須保留新的未用資料，並沿時間或實體邊界防止洩漏。

## 小結

- 先查警報原因，再決定是否觸發再訓練。
- 候選與現行用同一套獨立資料比較，整體、群體與資源都須過關。（補充）
- 通過後還需核准及分批線上驗證，重訓不保證改善。（補充）
