## 為什麼需要

模型上線後，收到的資料、使用方式和環境仍會改變。持續記錄這些狀況，稱為模型監控（Model Monitoring）。發現異常時通知負責人。再把問題交給負責更新模型的人。

常見問題（FAQ）的回答可能仍在引用舊條款。辨識影像的模型可能遇到光線太暗的環境。服務能回應，不代表答案正確。答案偶爾錯，也不代表模型需要重新訓練。

## 直覺

先看「送進來什麼」，再看「系統做了什麼」。最後拿預測和實際的正確結果比較，確認「做得對不對」。實際的正確結果稱為真值。

回應太慢或請求失敗，要另外調查服務出了什麼問題。這些狀況不能用來判斷預測對不對。

![系統依資料、預測與服務狀況發出警報。確認預測對錯時，要比對各筆預測和真值。發出警報後，仍要有人接手。](figure:l21302-model-monitoring-signals)

## 定義與公式

### 三類監控欄位

| 類別 | 保存欄位 | 能回答什麼 | 限制 |
|---|---|---|---|
| 輸入資料 | 欄位分布、缺值、畫質 | 資料是否不同或損壞 | 不直接代表效能下降 |
| 模型輸出及品質 | 分數、決策、版本；配對真值 | 決策如何變、是否正確 | 效能計算要等真值 |
| 服務 | 請求數、失敗數、延遲 | 是否可用、是否壅塞 | 成功回應未必答對 |

指引 5-19 把預測分布改變列在「模型漂移」之下，4-42 則談效能下降。兩種證據應分開記錄；預測分布變動本身不能確認概念漂移。完整辨別見資料漂移與概念漂移。

### 比率與觀察窗（補充）

$$
r=\frac{e}{n},\qquad n>0
$$

$e$ 是同版本、同一窗的錯誤事件數，$n$ 是相應的可評分事件數。預測錯誤用已配對真值的樣本；服務錯誤用請求，兩者分母不可混用。若沒有樣本，顯示「無法評分」並另查資料中斷。

服務某分鐘失敗 60／1,000＝6%。授信 W1 完整回收後錯 39／1,000＝3.9%；兩個百分比衡量不同問題。

### 警報後按什麼順序查

1. **資料與管線**：先查缺值、單位、重複、特徵時戳、來源及版本；排除資料傳錯。
2. **促銷與組成**：查活動時間、金額區間與客群占比；分布變動是線索，還不是根因。
3. **預測與真值**：比較決策比例，再以同一窗的成熟真值評分；另外看重要群體。（補充）
4. **責任及追蹤**：記誰接手、修管線或限制服務、是否產生候選，最後回看指標是否恢復。

:::supplement[來源：CMU SEI 漂移教學；本組教學回收規則]
授信真值延遲 30 天，窗結束時不能公布本期準確率。先追輸入及服務，另設真值回收率；到期後按原申請窗、版本及樣本 ID 補算，避免把成熟與未成熟資料混在一起。

人工抽查可提供較早線索，但須揭露抽樣方式。只收到客訴或只觀測核貸者時，真值可能有選擇偏差，不能直接當全部申請的品質。
:::

### 整體平均如何藏住長尾（補充）

以下均是授信完整真值回收後的重算。一般群固定 950 人，長尾群固定 50 人，占 5%；長尾是教學中預先定義的客群，並非 PSI 的分箱。

| 觀測窗 | 一般群錯誤／分母 | 長尾群錯誤／分母 | 整體錯誤／分母 |
|---|---|---|---|
| W0 | 19／950＝2% | 5／50＝10% | 24／1000＝2.4% |
| W1 | 19／950＝2% | 20／50＝40% | 39／1000＝3.9% |
| W2 | 38／950＝4% | 20／50＝40% | 58／1000＝5.8% |
| W3 | 19／950＝2% | 5／50＝10% | 24／1000＝2.4% |

若整體警戒線是 4%，W1 不報警；長尾警戒線 15% 卻已超標。先安排高傷害群體人工覆核，保留每群分母；樣本太少則補樣及查不確定性，不能直接判成沒問題。

線上紀錄含輸入分布、預測、成熟真值的群體錯誤、延遲與版本。訓練／驗證損失曲線是離線實驗紀錄；它不能證明今天的長尾群安全。

### 門檻與通知責任

指引舉錯誤率超過 5% 時通知團隊。本例把服務失敗率與預測錯誤率分開命名，並補上觀察時間及接手人。

:::supplement[來源：Prometheus Alerting rules；本組教學告警政策]
每分鐘各1,000次請求，失敗數40、60、70、60即4%、6%、7%、6%。每個窗結束才計數，大於5%連續三個完整窗，在第4窗結束觸發教學通知。

這不等同 Prometheus 的 `for: 3m`。若每分鐘窗尾評估，第2分鐘才首次成立，第4分鐘僅經過2分鐘；還要持續到第5分鐘才可能 firing。實際送達另受通知路由延遲影響。

門檻較低或等待較短，能早發現異常，也可能增加誤報；門檻較高或等待較長，則可能漏掉短暫但嚴重的事故。嚴重安全事件可另設立即止損規則。
:::

| 元件 | 本例工作 | 產物 |
|---|---|---|
| 日誌（Log） | 留請求ID、版本、失敗原因 | 可追查事件 |
| Prometheus（補充） | 收集時序指標、評估告警條件 | 待觸發／已觸發狀態 |
| Grafana（補充） | 呈現分窗、分版本儀表板 | 趨勢與調查入口 |
| 通知路由（補充） | 由 Alertmanager 等分組、送負責人 | 接手與升級通知 |

指引列出日誌分析與儀表板工具；上表各產品的具體職責是補充。看到儀表板不等於有人收到通知。

:::supplement[來源：Google SRE Monitoring；本組合成事件 INC-E-01]
處理單記「12:04通知，12:06接手，12:12修快取，12:20確認三窗恢復」。分布警報交資料工程師，品質交模型及風險負責人；API修復不能結案品質問題。
:::

### FAQ 與影像怎麼回退

FAQ 的過時答案和高併發變慢，分別需要品質回饋與資源／容錯處理。保留模型、知識及設定版本，才能追查是哪次更新造成差異。

1. 收集過時回答與使用者回饋，記模型及知識版本；查知識是否應更新，再評估是否重訓。
2. 併發造成失敗時先限制負載、優化資源，必要時轉人工或核准的固定答案。
3. 新模型與知識包先驗證，再受控更新；回退時一起核對模型、知識及路由。（補充）

:::supplement[來源：本組教學合成資料 L21302-E；Google SRE Canarying Releases]
faq-v1／kb-7 的 100 筆覆核有 18 筆過時；另 200 次併發請求失敗 12 次、p95 1,800 ms。兩種問題不能都交給重訓，先把高風險答案轉人工，分別修知識與服務瓶頸。
:::

視覺場域先查光照、模糊及網路延遲，並驗證每個版本在現場的表現。異常時可退回已驗證舊版，或以預設邏輯維持受控服務。

:::supplement[來源：本組教學合成資料 L21302-E；Google SRE Canarying Releases]
視覺W1模糊圖從2%升至18%，超過教學門檻10%，先通知現場工程師修光源及鏡頭。若新版另觸發回復條件，切回相容的inspect-v3／API v1／f1，核對載入與路由。

暗光也可能讓舊版失效；這時改用人工複驗或暫停自動放行，不能假設回退必定恢復。視覺真值延遲一天，未覆核的影像先標「待評分」。
:::

## 程式（補充）

下面從共用例子的授信 W1 擷取計數，演練群體警報。程式只做離線核算，沒有連到任何告警系統。

```python
groups = {"一般群": (19, 950), "長尾群": (20, 50)}
errors = sum(e for e, n in groups.values())
count = sum(n for e, n in groups.values())
if count == 0:
    print("整體 無法評分，追查回收或資料中斷")
else:
    print(f"整體 {errors / count:.1%}，超過4%：{errors / count > 0.04}")
for name, (e, n) in groups.items():
    if n == 0:
        print(f"{name} 無法評分，追查回收或資料中斷")
        continue
    rate = e / n
    alarm = "待補樣" if n < 50 else "品質調查" if rate > 0.15 else "持續觀測"
    print(f"{name} {e}/{n}={rate:.1%}，{alarm}")
```
```text
整體 3.9%，超過4%：False
一般群 19/950=2.0%，持續觀測
長尾群 20/50=40.0%，品質調查
```

:::tip[讀碼重點]
每群保留自己的分母；教學樣本下限 50 是調查規則，不是統計充分性的保證。真值未到齊時應先分流到回收追查，不能把未標註樣本填成正確。
:::

## 怎麼用、怎麼判讀

持續監控負責發現與派人處理；族群穩定性指數負責量化分布變化；重訓、重標註與版本回復處理資料工作流；再訓練驗證與版本晉升決定候選是否可上線。

### 換個場景

| 場景 | 先看什麼 | 處置重點 |
|---|---|---|
| FAQ、高併發客服 | 過時答案、回饋、延遲 | 分開查知識與容量 |
| 視覺現場 | 光照、畫質、延遲 | 現場驗證及預設容錯 |
| 零售促銷 | 消費金額分布、推薦品質 | 固定參考並查組成 |
| 授信（補充） | 成熟真值、5%長尾群 | 等到期並分群覆核 |
| 醫療分診（補充） | 後續診斷、漏診 | 優先處理高傷害案例 |

## 常見誤解

- 「警報一響就重訓。」先找資料、服務或環境原因，重訓未必適用。
- 「自動重訓會恢復原效能。」指引的成功案例不是保證，候選仍須驗證。（補充）
- 「預測分布變了就是概念漂移。」還缺輸入與真值關係的證據。（補充）
- 「真值未回收就是沒有錯誤。」那是未知，應追蹤回收率。（補充）
- 「整體合格就所有群體合格。」少數群可能被平均掩蓋。（補充）

## 進階

### 持續更新參考也要留下舊基準（補充）

業務永久改變後可以重新訂參考期，但先完成調查、核准及版本紀錄。保留固定舊基準有助觀察長期累積漂移；滾動基準則補看近期變動，兩者回答的問題不同。

## 小結

- 資料、預測與服務訊號分開記錄，預測品質要配對真值。
- 促銷警報先查管線，再查組成與效能，最後留下責任及追蹤紀錄。
- 整體平均之外要看群體分母與長尾傷害。（補充）
- FAQ 與視覺更新都要保留版本、回饋及可驗證的回退流程。
