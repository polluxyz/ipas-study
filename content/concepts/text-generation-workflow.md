## 為什麼需要

生成文字只是產製過程的一步。客服回覆、郵件、專業文書、程式補全與教材，各有不同的「可用」條件；文字通順仍可能漏掉條件或產生錯誤。

指引同時提醒真實性與長文一致性的挑戰。因此流程除了產出草稿，還要安排事實檢查與人工審核。

## 直覺

先決定要交付什麼，再整理依據，請模型生成草稿。收到草稿後，依任務標準檢查，未通過就修正，合格才交付。

## 定義與公式

文本生成（Text Generation）依提示產出自然語言內容。文本生成工作流則把需求、來源、草稿及驗收接起來；本頁以步驟說明，不需要公式。

指引的任務包括客服回覆、工作郵件與商業報告、合同草案與醫療報告、程式碼補全與除錯（如 GitHub Copilot），以及個人化教材。任務不同，交付前要確認的條件也不同。

:::supplement[來源：OpenAI Evaluation best practices]
以下把指引的任務展開成準備與驗收細節。

| 任務 | 生成前準備 | 人工驗收 |
|---|---|---|
| 客服、郵件與商業報告 | 對象、問題、可承諾事項 | 時限、語氣與承諾符合依據 |
| 合同草案、醫療報告 | 專業資料、用途、文件格式 | 由合適的專業人員確認內容 |
| 程式碼補全與除錯 | 既有程式及預期行為 | 工程師查邏輯並執行測試 |
| 個人化教材 | 學習目標、來源、程度 | 教師查內容及難度是否適合 |
:::

指引的原則是：生成內容要符合真實性與一致性，並安排人工審核。

## 走一次流程

使用 `L21103-C-generation.json` 的 CS01 與 ED01。兩份來源及所有候選都是合成資料，不含實際個資，也沒有呼叫生成服務。

1. 定義任務：CS01要摘要客服回覆時限；ED01要整理課程時間與上課方式。
2. 備妥來源：客服為「三日內回覆」；課程為「週三、線上」。
3. 形成草稿：讀取固定候選 A、B，當作兩個待驗收版本。
4. 查核關鍵條件：CS01的 B 改成一日；ED01的 B 改成實體，兩者都要修正。
5. 人工驗收：客服確認沒有額外承諾，教師確認通知內容，再交付使用。
6. 留下版本與回饋：將出錯的條件加入下次固定驗收項目。（補充）

### 兩份任務卡（補充）

客服提示可寫：「僅依來源整理回覆時限，不推測退款日期；缺資料時列待確認事項。」教材提示可寫：「給初學者的上課通知，保留日期與方式，缺漏不得自行補造。」

提示能說清邊界，仍需實際查核。若來源不足，先補資料或轉人工；檢索增強生成可以協助取回依據，但找到文件後仍要看草稿是否忠實使用。

## 怎麼用、怎麼判讀

先問「交付後會被怎麼使用」，再決定驗收證據。客服要能正確告知，程式要能執行預期功能，教材要讓指定程度的讀者學對內容。

:::supplement[來源：Claude Cookbook Building evals；OpenAI Evaluation best practices]
字詞指標可快速篩查候選，人工評估可看語意與可用性。兩者都要配合任務的硬條件；關鍵時限錯誤，不應由其他分數補成合格。
:::

### 換個場景

| 場景 | 來源或資料條件 | 驗收重點 |
|---|---|---|
| 客服、郵件與商業報告 | 有問題與可引用的通知 | 回覆是否符合條件及語氣需求 |
| 合同草案、醫療報告 | 有專業文件與使用目的 | 人工確認事實及專業內容 |
| 程式碼補全與除錯 | 有程式上下文與預期功能 | 修改後的行為是否正確 |
| 個人化教材 | 有學習目標與學生程度 | 內容、難度及例子是否合適 |
| 製造交班（補充） | 有事件紀錄與設備編號 | 不遺漏異常條件與待辦事項 |
| 博物館導覽（補充） | 有館藏資料與受眾 | 史實正確且敘述適合受眾 |

## 常見誤解

- 「生成完就能使用。」真實性、一致性與人工審核仍需確認。
- 「各種文件可共用同一驗收標準。」功能測試與專業審查需要不同證據。（補充）
- 「提示寫完整就不用看輸出。」提示能限定任務，不能保證每個條件都被遵守。（補充）

## 小結

- 先定交付需求，再備來源與生成草稿。
- 依任務確認真實性與一致性，並安排人工驗收。
- 客服、專業文書、程式及教材需要不同驗收證據。（補充）
- 固定來源與候選，才能追蹤修改是否改善結果。（補充）
