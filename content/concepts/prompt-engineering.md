## 為什麼需要

「幫我回覆」沒有說要分哪類、採何語氣，模型可能自行補足任務。提示設計（Prompt Engineering）把需求講清楚，讓輸出有可檢查的標準。

指引也提醒：提示不完整與生成的不確定性，都可能降低商業應用的可靠性。把格式寫清楚有幫助，卻不能因此省去事實查核。

## 直覺

提示像一張本次工作單：背景說明用途，任務指定動作，格式界定交付物，示例展示合格樣貌。一般提示推論的模型權重保持固定。

![沿箭頭看提示與來源進入固定模型，輸出還要經過驗收與迭代。](figure:l21103-prompt-engineering-flow)

## 定義與公式

本頁不需要數學公式，先分清示例放在哪裡。

| 方法 | 輸入有什麼 | 本次是否更新權重 |
|---|---|---|
| 零樣本推論（Zero-shot） | 任務指令，沒有解答示例 | 否 |
| 少樣本推論（Few-shot） | 指令加少量解答示例 | 否 |
| 監督式微調（補充） | 訓練用的輸入與理想答 | 是，更新選定參數 |

:::supplement[來源：Hugging Face Transformers Prompt engineering]
背景與來源文本最好有清楚邊界，並明列未知時的處理方式。資料中的指令未必可信，不能僅因出現在文件中就取得系統指令的地位。
:::

## 走一次流程

共用檔 `L21103-D-customization.json` 有客服、醫療各 20 筆。以下文字與輸出是人工編排的教學候選，沒有呼叫模型；用它練習驗收，不能宣稱提示已達到某種實測效果。

### 建立兩種任務工作單

語氣、風格、長度、格式是指引列出的四種控制欄位，應分別交代。

:::supplement[來源：Hugging Face Transformers Prompt engineering]
以下將 JSON 的 v1 提示展開成分行工作單，便於閱讀；它們不是 `prompt_trials.prompt` 的逐字引文。原始提示與候選可依案例 ID 對照共用檔。

「背景／任務」的分行寫法與客服、醫療兩個情境是本頁延伸，示範如何把控制欄位落到可驗收的工作單。

客服的背景是回覆諮詢，任務是分類後回覆。只依訊息與既定流程說明，不承諾尚未發生的退款。

```text
背景：你協助客服整理來訊。
任務：將 <訊息> 分為「退款」或「帳號」，再給下一步。
語氣：禮貌；風格：服務說明；長度：40 字內。
格式：「類別：回覆」；不得虛構退款進度或索取密碼。
<訊息>訂單金額 230 元，尚未出貨，想取消退款。</訊息>
教學候選：退款：請提供訂單編號以確認取消進度。
```

醫療摘要的背景是紀錄整理；任務只抽取已知事實，並指出原文沒有填的欄位。

```text
背景：你協助整理文字紀錄。
任務：抽出症狀及缺漏欄位，不新增診斷或處方。
語氣：中性；風格：紀錄式；長度：20 字內。
格式：「症狀；缺漏」。
<紀錄>主訴頭痛，已記錄症狀，未記載診斷。</紀錄>
教學候選：頭痛；診斷未記載。
```
:::

### 同一分類任務，改成零／少樣本

零樣本客服提示是：「將訊息分為退款或帳號，只輸出類別：帳號 S14 無法登入，想重設密碼。」教學候選為「帳號」，輸入沒有已解答的示例。

也可改寫為填空式（Prompt-based）：「帳號 S14 無法登入，想重設密碼。這則訊息的類別是＿＿。」若沒有附解答示例，仍屬零樣本提示。

少樣本版本在同一指令前加兩筆訓練示例：「未出貨想取消 → 退款」「登入失敗想重設密碼 → 帳號」，再放 S14。教學候選同為「帳號」；兩種版本都沒有更新權重。

:::supplement[來源：Hugging Face LLM Course 1.3；Transformers Prompt engineering]
示例固定取 S01、S02 的訓練部分；待判斷的 S14 屬驗證部分。測試資料不拿來挑提示，避免把對測試集的調整誤認成泛化能力。
:::

### 固定案例與迭代紀錄（補充）

固定用 S13、S14、M13、M14，比較 v0 與 v1。模型版本、解碼設定與種子也應記錄；本例沒有模型執行，只有相同輸入的人工候選對照。

客服兩案的 v0 原始提示都是「幫我回覆。」；醫療兩案都是「摘要一下。」。v1 才加入前述任務、四種控制欄位及來源限制；表中對照的是同一輸入的候選。

| 案例 | v0 候選問題 | v1 修改 | v1 候選驗收 |
|---|---|---|---|
| S13 | 虛構 230 元已核准入帳 | 指定類別、禁止虛構進度 | 格式、內容、依據通過 |
| S14 | 少了帳號類別 | 明列「類別：回覆」 | 格式、內容、依據通過 |
| M13 | 虛構已確診偏頭痛 | 限制只摘要原文 | 格式、內容、依據通過 |
| M14 | 原候選已合格 | 套同一範本複查 | 格式、內容、依據通過 |

驗收分三項：格式查欄位及字數；內容查是否完成任務；可靠性查每項主張能否回到原文。新提示修好某筆後，仍須重跑全部固定案例，檢查是否使原本合格的案例退步。

## 怎麼用、怎麼判讀

語氣可以從熱情改中性，風格可從行銷改紀錄式，長度與格式也要分別交代。「寫得簡短」比「20 字內、兩欄」模糊；明確限制有利驗收。

:::supplement[來源：Hugging Face Transformers Text generation；Prompt engineering]
固定種子與取樣設定可協助比較，但不保證跨硬體、版本的逐字重現。少樣本示例會占上下文；多放示例不必然更好，還要考量代表性與輸入長度。
:::

### 換個場景

| 場景 | 資料條件 | 判讀重點 |
|---|---|---|
| 郵件分類、產品情感 | 沒有或只有少量任務示例 | 用零／少樣本引導類別 |
| 生成內容客製化 | 有語氣、風格、長度、格式需求 | 分開檢查各控制欄位 |
| 醫療摘要（補充） | 僅有文字紀錄 | 不把缺漏寫成已知診斷 |
| 製造維修（補充） | 需依工單回覆 | 不憑語氣推斷故障原因 |

## 常見誤解

- 「提示有示例就會更新模型。」示例可只是推論上下文。
- 「格式全對，內容必定正確。」可控的格式與可信的主張要分別驗收。（補充）
- 「零樣本表示模型從未學過語言。」它指本次任務沒有解答示例。
- 「同一提示永遠逐字相同。」輸出仍受生成設定與模型條件影響。（補充）

## 小結

- 提示把任務、背景、輸出要求與示例交代清楚。
- 零樣本沒有解答示例，少樣本把示例放進上下文。
- 文字提示推論維持權重固定，與微調分開判斷。
- 格式、內容與可靠性要分別驗收。（補充）
