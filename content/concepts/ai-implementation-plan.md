## 為什麼需要

評估說「值得做」，仍未回答第一週做什麼、資料不夠時怎麼辦。AI 導入方案承接評估，將價值與可行性轉成具體工作。

產業條件會改變安排。製造重視感測資料整合與即時性，金融重視資料安全及法規，不能只換掉同一份計畫的公司名稱。

## 直覺

先圈出這次要完成的範圍，再把工作放進現有資源能承受的時程。

:::supplement[來源：Google「ML project planning」的 Scope down the project requirements]
範疇（Scope）回答「做哪些事、做到什麼程度」，也應說清楚本次不包含的工作。
:::

![沿評估、範疇、資源與主文件往下看；審查發現缺口時，需回到前面的安排重新調整。](figure:l21202-ai-implementation-plan-input-output)

指引強調情境導向、資源匹配與彈性調整。資料不足時先整理資料，比在不可靠的輸入上反覆訓練更符合這些原則。

指引的產能預測案例先用一個月改善感測資料收集，上線後產能效率提升 15%。同一企業的行銷與生產部門也可能有不同需求與優先順序，應分部門盤點，再安排導入。

## 定義與公式

導入規劃主文件是整體執行依據。背景、目標、策略、範疇、任務、時程、團隊與預算要放在同一套邏輯下。

### 可填的主文件

| 章節 | 要填什麼 | 核對什麼 |
|---|---|---|
| 背景與目標 | 問題、評估結論、成功指標 | 指標是否回答業務問題 |
| 策略與範疇 | 服務對象、納入與排除項 | 是否超過資料及技術條件 |
| 任務與產物 | 每項工作的輸入、輸出及驗收 | 有沒有未被承接的交付物 |
| 時程與團隊 | 工作窗口、負責角色、里程碑 | 人員與相依工作能否到位 |
| 資源與預算 | 人力、硬軟體、合作及來源 | 預算與任務是否相符 |

:::supplement[來源：Google「ML project planning」；「Stakeholders」]
每次更新另記版本、變更原因及核准者。把「兩週內驗證資料能否取得」寫成一個有期限的探索工作，能讓團隊決定繼續、縮小範圍或停止。
:::

## 走一次流程

以下共用 `L21202-A-projects.json`，兩案都是新編教學資料，並非前置財務單元的同一專案。

### 製造地端計畫摘要（補充）

1. 評估輸入：產品影像留廠內，服務回應上限 50 ms；覆核資料有 960/1,000 筆。
2. 目標與範疇：只做單一產線瑕疵提示，交由人員覆核，本次不自動停線。
3. 任務與角色：M1～M6 依序列出範疇、資料、模型、體驗、部署與驗收；每項指定主責及審查者。
4. 資源與時程：216 人時、八週、280,000 元；訓練使用地端 GPU，推論另配 CPU 節點。
5. 驗收：資料覆核比例至少 95%，瑕疵召回率至少 95%，並通過延遲、權限與操作測試。

主例子的資料覆核是 96%，符合資料門檻；模型假設計數為 100 件瑕疵檢出 95 件。這些只示範如何把條件寫清楚，尚不足以證明現場長期有效。

### 零售推薦計畫摘要（補充）

| 評估輸入 | 方案安排 | 資源或驗收 |
|---|---|---|
| 單一網店、尖峰 60 次／秒 | 只改推薦區，不自動調價 | CPU 容量估算及壓測 |
| 顧客行為資料有用途限制 | 使用經審查的去識別化資料 | 權限與用途審查 |
| 離線比較需要一致基準 | 固定時間切分、100 次留出請求 | 前五名命中率至少 68% |
| 部門人員與預算已盤點 | R1～R6、176 人時、八週 | 218,000 元及四類審查 |

### 資料不足時怎麼重排（補充）

製造案新增批次有 200 筆，只有 140 筆覆核。先暫緩把這批資料納入模型，請資料工程師補覆核，再重估模型與測試窗口；既有切分不任意改動。

本例變更多需 16 人時及 6,000 元硬軟體，試辦改到第十週、總額 302,000 元。負責人送審追加款與時程，尚未核准前不得把新日期當成已承諾的交付。

## 怎麼用、怎麼判讀

看計畫時，逐項問「這個目標靠哪項任務、哪個人、什麼資源完成」。如果只有願景或設備清單，還沒有形成可執行方案。

:::supplement[來源：Google「Stakeholders」的 Deliverables]
跨成果核對時，讓任務 ID 串起主文件、時程、預算與驗收。M5 的 API 若改版，部署說明及測試引用也要一起更新；檔名相同不代表版本一致。
:::

### 換個場景

先看指引的產業與資料條件，再把同一套規劃問題換到其他服務。

| 場景 | 規劃重點 |
|---|---|
| 製造感測整合、金融安全合規 | 依資料即時性或治理限制安排工作 |
| 零售銷售預測、醫療診斷輔助 | 先界定業務目的，再選資源與驗收 |
| 資料品質不足或感測資料不全 | 先整備資料，再重排模型與時程 |
| 交通號誌建議（補充） | 限定試辦路口與人工接管條件 |
| 公共服務分流（補充） | 明定轉人工及民眾申覆流程 |

## 常見誤解

- 「評估通過就等於能開發」：還需把人員、資源與工作接起來。
- 「計畫不能改」：需求與技術條件變了，時程和策略也要調整。
- 「先買最大 GPU 就完成規劃」：設備沒有回答目標、責任或驗收。
- 「改完簡報就算改完方案」：附件的版本、期間與引用也要一致。（補充）

## 進階

### 探索也有交付物（補充）

探索工作可以交付「哪些方法無效、資料還缺什麼」，但要有時間界線與紀錄。它提供下一次資源決策的證據，不保證模型品質隨工時等比例上升。

## 小結

- 評估結論要轉成目標、範疇、任務及資源。
- 依產業和資料條件安排方案，資料不足先補資料。
- 主文件、時程、團隊與預算需互相對應。
- 變更保留原因、版本與核准紀錄。（補充）
