## 為什麼需要（補充）

RAG 的使用者可能只問一句話，模型卻同時讀入指令、歷史與多份文件。只數問題字數，會低估費用與輸入長度。

本頁先用自訂單價拆帳，再比較快取與縮減輸入。以下成本方法是補充目標；每一個數字都是教學假設，不是產品報價或實測成效。

## 直覺

檢索增強生成（RAG，英文 Retrieval Augmented Generation）先找相關外部資料，再讓模型參照資料回答。指引用知識問答、醫療文獻查詢說明需要背景知識的用途。

:::supplement[來源：Claude Academy「How context affects Claude's performance and cost」；Anthropic「Prompt caching」]
把一次輸入分成四包：固定前綴、當次問題、對話歷史、檢索資料。快取重用相同前綴的計算；摘要或刪除不相關文件，才會減少送入的內容。

兩者不能混算：快取仍提供完整資訊，摘要則可能遺失條件。先知道哪一包最大，才知道改哪裡最可能省錢。
:::

## 定義與公式（補充）

### 先數完整輸入

沿用斷詞與子詞切分的原則：token 不是固定一個中文字。實際數量應用候選模型的切分器或計量工具確認，本例直接給定各包的 token 數。

四包是本例互不重複的分區，全部輸入都歸入其中。上下文要同時容納輸入及預留輸出；命中的快取前綴仍占容量。

$$
I=P+Q+H+R,\qquad I+O_{\max}\leq L
$$

$I$ 是完整輸入，$P$ 是前綴，$Q$ 是問題，$H$ 是歷史，$R$ 是檢索資料。$O_{\max}$ 是預留輸出，$L$ 是上下文上限；單位皆為 token。

客服的完整輸入是四包相加：

$$
I=800+200+2{,}000+2{,}000=5{,}000
$$

預留輸出 800、上限 6,000，總長為 $5{,}000+800=5{,}800$，可容納。命中快取仍按完整 5,000 檢查。

### 普通輸入、輸出分項算

$$
\begin{aligned}
C&=\frac{N}{U}(Ip_i+Op_o)\\
s&=\frac{C_0-C_1}{C_0}
\end{aligned}
$$

$N$ 是每日請求數；$U$ 是單價單位，本例為 1,000 token；$p_i,p_o$ 分別是每 $U$ token 的輸入、輸出單價。$O$ 是平均實際輸出量，$C$ 是每日生成費，單位元／日。

$C_0,C_1$ 是優化前後同範圍的費用，$s$ 是節省比例，僅在 $C_0>0$ 時定義。費用看平均實際輸出，長度看預留上限。

客服代入每日流量與假設單價：

$$
C_0=\frac{10{,}000}{1{,}000}(5{,}000\times0.02+500\times0.04)=1{,}200
$$

輸入降到 3,000 後 $C_1=800$，故 $s=400/1{,}200\approx33.33\%$。完整代入可在「算一次」與程式中核對。

### 前綴快取另算讀、寫

$$
C_{\mathrm{cache}}=\frac{N}{U}\left[(I-P)p_i+P\bigl(hp_r+(1-h)p_w\bigr)+Op_o\right]
$$

$h$ 是完整命中前綴的請求比例，介於 0 與 1；$p_r,p_w$ 是每 $U$ token 的快取讀、寫單價。假設未命中均寫入同長前綴，沒有其他費用。

本例假設服務允許客服 800、醫療 1,000-token 前綴快取，且無額外最低長度限制；不是特定產品的費用預測。

引用文件的門檻依模型而異。例如 Claude Sonnet 4.6 最低需 1,024 token，兩案前綴都不合格，不能套用本例命中率。實務先查候選模型的資格，再算讀寫費。

客服 $P=800,h=0.75,p_r=0.002,p_w=0.025$。普通輸入 840、讀取 12、寫入 50、輸出 200，合計 1,102 元／日。

若各請求命中長度不同，要逐筆累加各類 token，不能只套一個請求命中率。真實服務若另收儲存、工具或檢索費，也應另外列入預算。

## 算一次（補充）

### 同一批輸入，比較不同修改

`L21202-C-decision-inputs.json` 連回兩領域各 100 筆原流程索引。成本按每日流量外推；品質只比 v2 探索 80 筆，不算獨立確認。

客服假設每日 10,000 次，輸入／輸出每千 token 分別 0.02／0.04 元。下圖由同一份 JSON 計算，輸出固定每次 500 token。

![先比基準與合併策略各組成的輸入量，再比每日總生成費；輸入量降幅不等於總費用降幅。](figure:l21202-rag-token-budget-input-budget)

| 策略 | 輸入 token／次 | 每日生成費 | 品質假設：符合／80 |
|---|---|---|---|
| 基準 | 5,000 | 1,200 元 | 76 |
| 歷史 2,000→800 | 3,800 | 960 元 | 76 |
| 檢索 2,000→1,200 | 4,200 | 1,040 元 | 76 |
| 合併兩項 | 3,000 | 800 元 | 76 |
| 只快取前綴，命中 75% | 5,000 | 1,102 元 | 不刪內容，仍須同條件驗 |

本例每日生成費預算 900 元，合併策略的 800 元在額度內，單做摘要的 960 元仍超額。省錢與品質都達標才是候選；表中品質是合成設定，尚未執行生成模型。

快取命中率若改為 25%，每日費用是 1,194 元；完全沒命中是 1,240 元，反而高於不快取的 1,200 元。原因是本例的寫入單價高於普通輸入價。

### 換到醫療文件核對

每日 2,000 次、每次輸入 6,000、輸出 600，基準生成費為 $2{,}000(6{,}000\times0.02+600\times0.04)/1{,}000=288$ 元。

歷史 2,400→1,200、檢索 2,400→1,600 後，完整輸入為：

$$
I=1{,}000+200+1{,}200+1{,}600=4{,}000
$$

每日 208 元，低於本例 220 元額度；仍須保留文件版本與人工確認。

## 程式（補充）

兩段程式依序執行，只做預算算術，不連 API。數值取自共用 JSON 的客服規格；沒有亂數，所以不需要種子。

```python
from decimal import Decimal as D
n, unit = D(10000), D(1000)
prefix, question, history, retrieval, output = map(D, [800, 200, 2000, 2000, 500])
pi, po = D("0.02"), D("0.04")
base_input = prefix + question + history + retrieval
short_input = prefix + question + D(800) + D(1200)
def bill(tokens):
    return n * (tokens * pi + output * po) / unit
base, short = bill(base_input), bill(short_input)
print(f"輸入 {base_input} -> {short_input} token/次")
print(f"每日生成費 {base:.2f} -> {short:.2f} 元")
print(f"輸入節省 {(base_input-short_input)/base_input:.2%}")
print(f"總費用節省 {(base-short)/base:.2%}")
```
```text
輸入 5000 -> 3000 token/次
每日生成費 1200.00 -> 800.00 元
輸入節省 40.00%
總費用節省 33.33%
```

:::tip[讀碼重點]
`output` 在兩次 `bill` 都保留。`Decimal` 使用字串單價，避免把二進位浮點近似當成帳務差異。
:::

```python
read_price, write_price = D("0.002"), D("0.025")
for h in map(D, ["0", "0.25", "0.75"]):
    prefix_fee = prefix * (h * read_price + (1-h) * write_price)
    daily = n * ((base_input-prefix) * pi + prefix_fee + output * po) / unit
    print(f"命中 {h:.0%}：每日 {daily:.2f} 元")
print("長度預算", base_input + D(800), "<=", 6000)
```
```text
命中 0%：每日 1240.00 元
命中 25%：每日 1194.00 元
命中 75%：每日 1102.00 元
長度預算 5800 <= 6000
```

:::tip[讀碼重點]
未命中使用 `write_price`，不是零元；長度檢查仍保留完整前綴，不能扣掉命中的 token。
:::

## 怎麼用、怎麼判讀

### 快取、摘要與檢索各改什麼（補充）

| 方法 | 要有的條件 | 品質與成本檢查 |
|---|---|---|
| 靜態前綴快取 | 相同模型及可重用前綴；符合長度與有效期規定 | 看讀、寫用量，不把內容相似當完整命中 |
| 歷史摘要 | 舊對話較長，能保留任務狀態 | 保留否定、例外、日期、金額與待辦；計入摘要本身的費用 |
| 檢索縮減 | 有重複或不相關文件，可先篩選或重排 | 檢查來源覆蓋與關鍵例外，不能只追求文件變少 |

固定規則放在前面，個別問題及變動檢索放後面，有助於重用穩定前綴。若把每次都不同的時間戳放在最前，即使後面的長段內容相同，這段完整前綴也無法命中。

摘要和檢索可先分別比較，再驗合併策略。客服長歷史較大，先驗摘要有理由；若主要成本來自輸出，單改輸入的收益就有限。

### 資訊遺失反例與驗證（補充）

客服原規則是「簽收後七日內申請，已拆封耗材除外」。若摘要只留下「七日內可退」，起算點與例外消失；醫療文件的「過敏欄記載無」，也不能摘要成「病人沒有過敏」。

本例過度摘要只剩 72/80 符合，低於事前 76/80 門檻。應保存必要條件，按相同索引檢查正確、引用、例外及拒答，再用新確認資料驗改版；不是先降低門檻。

成本表未包含摘要模型、文件嵌入、檢索、儲存與人工維運。若新增這些支出，須補回 AI 導入總成本，才能判斷整體是否划算。

## 常見誤解（補充）

- **輸入減少 40%，總費用也減少 40%**：輸出不變時，降幅要從完整費用重算。
- **快取等於把文件刪掉**：資訊仍供模型使用，也仍占上下文長度。
- **摘要越短越好**：短到刪掉例外，可能省費卻使回答失準。
- **把命中率設成 100% 就完成預算**：應以實際讀寫用量查核，包含冷啟動與過期。

## 進階

### 併用後要再量（補充）

客服合併摘要與檢索後，若前綴仍是 800、命中仍為 75%，代入快取式得到每日 702 元。但這是再一組條件假設，不代表修改後一定維持相同命中率。

## 小結（補充）

- 輸入、輸出分項算，再用同範圍費用算節省比例。
- 快取看穩定前綴與實際命中，未命中寫入可能增加費用。
- 歷史摘要與檢索縮減能減少輸入，也可能刪掉關鍵條件。
- 先驗品質及上下文上限，再把所有新增費用補回預算。
